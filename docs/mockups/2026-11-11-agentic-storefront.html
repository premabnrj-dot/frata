Proposal · 11 Nov 2026 · for the owner

Frrata Sites: storefronts as code, built by developers and agents

Frrata becomes the commerce backend: console, integrations, catalogue, checkout and the Storefront API. Each shop's website is its own code, in its own repository, deployed on its own. Developers write it by hand or with Frrata's agent; partners publish agentic starters that anyone can build from. Themes and the customizer retire.

The shift in one picture

The decision this needs first

Frrata's goal today is that a small fashion brand keeps more profit per delivered order without a developer. This proposal makes developers the core client of the storefront. The two can sit together: the console stays for the brand, and the agent stands in for the developer a brand doesn't have. That is still a change to the north star, so it is yours to write.

Proposed wording: "Frrata is the commerce backend for Indian D2C brands. A brand runs its business in the console; its website is code that a developer, a partner or Frrata's agent builds on the Storefront API. Frrata keeps what makes the brand money: catalogue, checkout, COD, payments, orders, shipping, GST."

Two earlier decisions reverse with it, and both are recorded as yours (2026-11-11): the Storefront API was parked ("everything runs on Frrata for now"), and the in-console Claude builder was skipped ("Claude never runs on Frrata's servers"). This proposal un-parks the first and brings the second back, inside a sandbox.

What stays, what goes, what comes

Stays

  • Console: orders, COD risk, NDR, inbox, campaigns, analytics, GST
  • Integrations: Razorpay (shop's own account), Shiprocket, Meta, WhatsApp, Google
  • Catalogue, offers, media, collections
  • Checkout, bag, order pages, policy pages on Frrata's host
  • EkCode sign-in
  • Tenancy (ADR-0002), integer paise (ADR-0004), outbox (ADR-0006), costs never in a browser (ADR-0003)

Goes (frozen, then removed)

  • Theme catalogue and manifests: 6 themes, 21 versions src/domains/themes (56 files, 4,014 lines)
  • The customizer and Look (lookeditor), console/look (27 files, 3,097 lines)
  • Theme Studio TS1c–TS4, designs and blocks, ADR-0012 (manifests as data)
  • Section library renderers components/storefront (47 files, 3,342 lines), after migration
  • Theme release flow in Admin; shop pages as data (TS1a)

Comes

  • Storefront API, un-parked, then grown: read, cart, customer, webhooks
  • One repo and one isolated deployment per shop, on Frrata's hosting account
  • The builder: chat, live preview, files, checks; the agent works in a sandbox
  • The gallery: agentic starters (code + design rules + agent skill) by Frrata and partners
  • Developer access: keys, git, CLI, docs, OpenAPI, an MCP server
  • Publish checks: build, speed, accessibility, legal block, secrets, dependencies

What a "theme" becomes

An agentic starter in the gallery: a working storefront repository, its design rules (tokens, type, components) and a skill that tells the agent how to extend it without breaking it. A brand picks one; the agent builds the brand's site from it in the brand's own repo. Nothing is customised through forms any more; the brand asks, the agent changes code, and the checks decide whether it can publish.

One lesson from the market shapes this. A copied theme stops getting its author's updates (Shopify's AI theme editing works on a duplicate theme for this reason). So a starter ships its updates as skills and migrations the agent applies on request, not as files that overwrite the brand's code.
