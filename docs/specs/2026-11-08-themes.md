## Goal
North star (5) **a premium-looking storefront**, with (4) **mobile checkout conversion**: a better-looking, fast shop
turns more Instagram visits into delivered orders, and the delivered-order fee is how Frrata earns.
**Measures:**
- T1: share of open shops that publish a customized theme within 14 days.
- Sessions → delivered orders, before and after publishing (per shop, 28 days each side).
- Field speed (from T2): p75 LCP ≤ 2.5 s and INP ≤ 200 ms on ≥ 90% of shops. Lab budget from T0: Lighthouse mobile ≥ 90.

## Job
A brand owner (or their partner) picks a look made for what they sell, makes it theirs in minutes on a phone or a
laptop, and publishes it without a developer and without ever breaking the shop. Frrata's own team builds and
releases themes safely.

## The model

A **theme** is data over one section library that Frrata owns:

```
Platform defaults  →  Theme version manifest  →  Style (preset)  →  The merchant's layer  =  resolved theme
(code)                 (code, immutable once         (in the            (shop_theme_revisions.settings,
                        released)                     manifest)          validated by Zod at every save)
```
`resolveTheme(manifest, styleKey, layer)` in `src/domains/themes/resolve.ts` (pure) merges top-down and returns a
fully typed `ResolvedTheme` (tokens + header + footer + page templates). Rendering reads only `ResolvedTheme`.

### What is code and what is data
| Thing | Lives in | Changes by |
|---|---|---|
| Section components (React Server Components, each ≤ 1 small client island) | `src/components/storefront/sections/<key>.tsx` | Pull request + gates |
| Section settings schemas (Zod) and defaults | `src/domains/themes/sections/<key>.ts` (pure, used by the customizer and the renderer) | Pull request + gates |
| Theme manifests | `src/domains/themes/catalogue/<theme>/<version>.ts` (a typed object, not JSON on disk) | Pull request + gates; immutable once released (T3 makes this enforceable) |
| Theme colours (hex) | Only in manifests; `check:hex` allows `src/domains/themes/catalogue/**` and nothing else new | — |
| The merchant's layer | `shop_theme_revisions.settings` (jsonb **content**, never state) | The customizer |
| Which revision is live | `shop_theme_publishes` (append-only rows; latest = live) | Publish / Restore / Undo |

### The manifest (TypeScript type, checked by `check:theme`)
```ts
type ThemeManifest = {
  key: 'classic' | 'editorial' | 'bazaar' | 'minimal' | 'atelier'
  version: string                 // semver, '1.0.0'
  name: string; job: string       // "Big photos, serif type. For designer ethnic wear."
  goodFor: Sells[]                // from shop_settings.sells values
  features: string[]              // "What it has", ≤ 8 lines
  speed: number | null            // Lighthouse mobile, written by themes:shots
  styles: { key: string; name: string; schemes: Record<SchemeKey, Scheme> }[]   // 1–3
  defaults: ThemeSettings         // § Theme settings
  allowed: { headers: HeaderVariant[]; footers: FooterVariant[]; sections: SectionKey[]; pairings: PairingKey[] }
  home: SectionInstance[]         // the starting Home
  migrations?: { from: string; to: string; run: (layer: unknown) => unknown }[]   // T3
}
type Scheme = { bg: Hex; text: Hex; sub: Hex; line: Hex; chip: Hex; accent: Hex; onAccent: Hex; sale: Hex }
type SchemeKey = 'paper' | 'tint' | 'ink'    // shown as the style's names, e.g. Paper / Haldi / Ink
```
`check:theme` (new gate) for every manifest:
- Zod-valid; keys unique; every `home` section is in `allowed.sections`; ≤ 20 sections on Home.
- **Contrast per scheme**: text/bg ≥ 4.5, sub/bg ≥ 4.5, accent/bg ≥ 3 (fills, lines), onAccent/accent ≥ 4.5, sale/bg ≥ 4.5.
  The same function the merchant's brand colour is checked with (`src/domains/themes/contrast.ts`, reusing
  `scripts/check-contrast.mjs`'s maths through a shared pure module).
- Every pairing loads only its families' Latin subset; Devanagari only when a name needs it (as today).
- A released version's file is unchanged (T3: its sha256 matches `theme_versions.manifest_sha256`).

enforced by its Zod schema; the customizer shows the limit as a counter (e.g. "34 / 80").

Rules every section obeys:
- Text is plain or the small rich-text AST (paragraphs, bold, italic, shop links). No HTML, no markdown, no script.
- Links are **shop paths** chosen from a picker (`/collections/…`, `/products/…`, `/policies/…`), validated
  against the shop's own handles at save and at render (a deleted collection renders nothing, the customizer flags it).
- Images are the shop's own media in Blob (the existing upload path and `PATH_SHAPE`), widths from
  `src/domains/media/sizes.ts`; `alt` is required (empty only with "decorative" ticked).
- A section whose data is empty renders nothing on the shop and says why in the customizer
  ("No products are new in the last 30 days").
- **Drop teaser** hides itself when its date has passed (`now` passed in; the cached page revalidates at the date).
- **Shop by promise** words come from the facts, so a promise cannot be false; switching COD off removes it.

### Sources (the "shortcodes"), `src/domains/storefront/sources.ts` (pure)
`source(catalogue, facts, params, now) → productIds[]`, resolved on the server inside the cached shop read.

| Source | Params | Fact | Notes |
|---|---|---|---|
| New in | days 30 / 60 / 90 | `products.publish_at ?? created_at` | Listed products only (`isListed`) |
| Best sellers | days 30 / 90 | **delivered units per product** over the window | A new cached read `bestSellerOrder(tenantId, days)` returns **ordered ids only**, tag `shop:<id>:catalogue`, revalidate 1 h. Counts never leave the server (ADR-0003 holds by construction) |
| A collection | collection | existing `inCollection` | — |
| Under a price | max ₹ | `priceOf(p).min ≤ max` | — |
| On sale | — | any variant `compareAt > price` | — |
| ~~Back in stock~~ | — | needs a restock timestamp | **T2** (adds `variants.restocked_at`, set by the stock write path) |
| **Never**: by margin or profit | — | — | A ranking by margin leaks cost order (ADR-0003). `check:theme` refuses a source key outside the list |

### Switching themes ("Try X in a draft")
The draft is a new revision of theme X. Carried over by `carryOver(fromLayer, toManifest)` (pure, tested):
brand colour, pairing (if allowed), corners, photo shape, announcement text, and **every Home section whose key X
allows** (same order, same settings). The rest takes X's defaults. The dialog after switching lists what did not come
across ("Category circles header isn't in Minimal"). Nothing changes for shoppers until Publish.

### Revisions, drafts, publish, history (data and rules)
- **One open draft per shop**: the newest revision whose `created_at` is after the latest publish's revision.
  Autosave updates it in place (debounced 800 ms; "Saving…" → "Saved"; offline → "Not saved. Retrying.").
- **Concurrency**: each save sends the draft's `version` (an integer bumped on every save). A stale save is refused:
  "Riya changed this draft a moment ago. Reload to see her changes." (two people editing; no merge, KISS).
- **Undo / Redo**: client history of the draft's layer for this session (50 steps), each step re-saved. Not a server log.
- **Publish** (owner or admin, not support): inserts `shop_theme_publishes(revision_id)`, then `refreshShop(tenant,'shop')`.
  The draft row becomes that published revision; the next edit opens a new draft copied from it.
- **History**: every publish (and the open draft); **Restore** = a new draft copied from that revision.
- **Undo after publish** = publish the previous published revision again (a new row; history shows both).
- **Discard draft** = delete the open draft row (the only delete; published revisions are never deleted).
- **Validation**: every save is parsed by the version's Zod schema; an invalid layer is never stored. Errors that can
  only be judged against live data (a deleted collection, an image removed) are warnings in the customizer and
  render nothing on the shop.
- **Pruning**: drafts never published and older than 90 days are deleted by the daily cron (YAGNI on keeping them).

### Preview
- `/console/preview/theme/[[...path]]` renders the shop with a **revision id** (the member's own shop only;
  `requireMember`, the revision must belong to the tenant, read inside `withTenant`), `dynamic = 'force-dynamic'`,
  `Cache-Control: private, no-store`, `noindex`.
- The customizer shows it in an `<iframe>` on the same origin. **Today every response sends `X-Frame-Options: DENY`
  and `frame-ancestors 'none'`**: the preview route alone gets `frame-ancestors 'self'` and no `X-Frame-Options`
  (a `headers()` entry for `/console/preview/theme/:path*` placed after the global one; a test asserts every other
  path still sends DENY).
- After each autosave the customizer posts `{type:'refresh'}` to the iframe, which calls `router.refresh()`;
  selection is `{type:'select', sectionId}` → the iframe scrolls to and outlines the section. Messages are checked
  for `event.origin === location.origin` both ways.
- "Preview" in the top bar opens the same route in a new tab, full size. **No public preview links** (owner call 5).

### Rendering and caching (the shop)
- `shopTheme(tenantId)` (new cached loader, tag `shop:<id>`) reads the latest publish's revision → `{key, version,
  settings}`; the manifest comes from the code registry; `resolveTheme()` runs at render.
- A shop with **no publish row** renders Classic built from today's `accent` and `display_font` (T0 behaviour, and the
  fallback forever: a shop can never render "no theme").
- Publish → `refreshShop(tenantId, 'shop')`: every page of that shop re-renders on its next request. No other shop moves.
- Tokens are CSS custom properties on `[data-store-theme]` (as today's `--store-*`), set from `ResolvedTheme` in an
  inline `style` on the shell. **No per-shop CSS file, no runtime CSS-in-JS.**
- Fonts: `next/font` for the 5 pairings' families, Latin subset, `display: swap`, loaded only by shop pages (as
  `shop-preview/fonts.ts` today). The shell sets which family each role uses.
- Script budget: unchanged 120 kB; sections are server components; client islands allowed only for the bag, the
  phone menu sheet and the rail's scroll buttons.

## Admin: building and releasing themes (T0 → T3)

There is **no zip or code upload** at any phase before T4, and none of code at all (owner call 1). A theme's code ships
the way all Frrata code ships: a pull request, the gates, a merge to `main`, a Vercel deploy.

### How a Frrata developer builds a theme
1. Branch. Add or change sections in `src/components/storefront/sections/` + their schemas in `src/domains/themes/sections/`.
2. Add a manifest `src/domains/themes/catalogue/<theme>/<semver>.ts`. A new version never edits an old file;
   a breaking change to a section's settings adds a `migrations` entry (pure, with a vitest case per step).
3. `npm run themes:dev` serves a fixture shop (`e2e/fixtures/themes/*`: 3 shops — ethnic with 40 products,
   basics with 12, made-to-order with 6 — with real-looking photos from the seed) at `/console/preview/theme` per
   theme × style.
4. Gates (local and CI): `check:theme`, `check:hex`, `check:contrast`, `check:scale`, vitest, `npm run themes:shots`
   (Playwright: a phone and a desktop screenshot per theme × style of each fixture shop, and the **visual diff**
   against the committed baseline; an intended change updates the baseline in the same PR) and `npm run themes:speed`
   (Lighthouse mobile on each fixture shop: performance ≥ 90, accessibility ≥ 95, SEO ≥ 95, CLS ≤ 0.05; the score is
   written into the manifest's `speed`).
5. Review by a second person (or the `impact-reviewer` agent) and merge. The deploy makes the version **available**.

### How Admin releases it (T3)
| Step | Admin | What a merchant sees |
|---|---|---|
| Deployed | Admin › Themes lists versions found in the deployed code that have no `theme_versions` row: "New in this deploy: Editorial 1.1" with **Add** | Nothing |
| Added | A `theme_versions` row: key, version, manifest snapshot (jsonb, content), `manifest_sha256`, gate report (speed, checks), `added_by` | Nothing |
| **Staged** | "Stage to shops…" picks pilot shops (search by name; Frrata's own shops first); `theme_version_stages(tenant_id, version_id)` rows | Pilot shops see "Editorial 1.1 is ready" |
| **Released** | "Release to everyone" sets `released_at/by` (admin role only, a confirm dialog naming how many shops are on the older version) | Every shop on Editorial 1.x sees the update panel; new installs get 1.1 |
| **Recalled** | "Recall 1.1" with a reason: sets `recalled_at/by/reason`. New installs and updates stop | Shops whose **draft** is on 1.1 see "Editorial 1.1 was withdrawn: your draft moves back to 1.0" (migrated back if a reverse migration exists, else their last 1.0 revision). **Live shops keep rendering 1.1** (it still exists in code) and see "Restore your previous look" in one tap |
| **Withdrawn** (security only) | "Withdraw now" (admin, typed confirmation): live shops on it render their **previous published revision** at once; audited | A notice in Look: "Frrata withdrew Editorial 1.1 for a problem. Your previous look is live." |
State is derived from the timestamps (`added_at`, `released_at`, `recalled_at`, `withdrawn_at`) and stage rows; there is
no status column. Every Admin action writes an `audit_events` row (`auditStaff`).

**Before T3** (T1, T2): every manifest in the deployed code is available to every shop at once; a bad theme is
reverted by a pull request (the previous version's file is still there, so live shops keep rendering).

### Updating a shop to a new version (T3)
"Preview the update" creates a draft on the new version: `migrate(layer, from, to)` runs the manifest's migrations in
order; a missing step means the update is not offered (`check:theme` fails a release without a path from every
released version). Nothing is live until the merchant publishes.

### T4 (later, signal-gated): partners author themes as data
A partner package is **JSON only**: a manifest that uses existing sections and tokens. Uploaded in Partner › Themes,
parsed by the same Zod schema and `check:theme` in the browserless server (no code runs), screenshotted and
Lighthouse-checked by a job on fixture shops, then a review queue in Admin (approve / request changes with reasons).
New sections still come only by a pull request to Frrata's library. Payouts need Phase 6 billing and a CA opinion.

## Design review (frata-planning § 3)

**UI/UX.** One primary action per screen: Customize (Look), Publish (customizer), Try in a draft (details).
States: fresh shop (Classic, never customized: "Customize" still primary; the gallery explains "Classic is your shop
today"), draft exists, publishing, published, publish failed ("We couldn't publish. Your draft is safe."), stale draft
(another person), a section with no data, a deleted linked collection, an image with no alt (blocks Publish, named),
no permission (staff/partner: Publish replaced by "Ask the owner to publish"; partners may edit drafts — `CAN_BUILD`),
support visit (read and preview only), phone (bottom sheet; Publish in the header), offline. Keyboard: every list row
has Move up/down and Hide as buttons; Undo `⌘Z`, Redo `⌘⇧Z` scoped to the customizer; the preview iframe has a
title. Norman: signifiers (drag handle + buttons), mapping (selected section outlined in the preview), constraints
(limits as counters, only allowed variants shown), undo everywhere (Undo, History, Restore, Undo after publish),
feedback (Saved state, publish toast), recognition over recall (picture cards, style swatches, phone preview).

**Tenancy.** Two new tenant tables in T1 with the standard policy; composite FKs keep a revision and a publish in one
tenant; the preview route takes the revision id from the URL but reads it **inside the member's tenant
transaction**, so another shop's id returns nothing (proof: A cannot preview, publish or restore B's revision; a
publish pointing at B's revision fails the FK). Platform `theme_versions` is readable by every shop (no tenant data).
Theme media lives under `tenants/<id>/theme/` (existing `PATH_SHAPE` extended, proof that a path for B is refused).

**Modularity.** Pure: `src/domains/themes/` (manifest types, `resolveTheme`, `carryOver`, `diffLayers`, migrations,
contrast, section schemas) and `src/domains/storefront/sources.ts`. Reads: `src/lib/queries/themes.ts`. Writes:
`src/app/(console)/console/look/actions.ts` through `asMember` (themes are core, not a module: every shop has a
look). Rendering: `src/components/storefront/sections/*` and the shell. Offers and Reviews plug into themes only
through slots (T2), never by editing sections (agreed with the brand session, 2026-11-08).

**SSOT / DRY.** Live look = latest publish row (derived). Draft = newest revision after it (derived). Promise words =
shop facts. Logo, social handles, policies = Settings. Best sellers = delivered units, computed once in one cached
read. Colours: manifests only (gate). Contrast maths: one module for the gate and the brand colour check.

**YAGNI.** Out: a free page builder, per-element styles, custom CSS, font upload, Liquid/DSL, code upload, public
preview links, A/B testing, scheduled publish (T3 maybe), theme duplication, multi-language strings (T2), the
WhatsApp sign-up footer (C2 consents), "Back in stock" (T2), premium prices (after the smoke test).

**KISS.** T1 is two tables, a code registry of five manifests, eleven sections, one pure resolver, an iframe preview
that refreshes after each autosave. Puck is **not** adopted in T1: our sidebar is a list of typed forms over Zod
schemas (each control a design-language primitive); a spike in T1·0 confirms the iframe refresh stays under 1 s, and
only if it does not do we revisit a client renderer.

**Scalability.** 500 shops × ≈ 50 revisions a year ≈ 25k rows; settings ≤ 32 kB each (Zod caps lengths and counts).
Autosave is ≤ 1 write per 800 ms per editor. The shop read adds one indexed lookup to the cached shop load. Best
sellers is one grouped query per shop per hour (index `orders(tenant_id, delivered_at)` exists? → the plan checks
and adds it if not).

**Performance.** Storefront stays static per shop (ISR, tag `shop:<id>`); tokens are inline custom properties; no
new client JS on shop pages beyond the existing islands (+ the menu sheet and the rail buttons, ≤ 6 kB). Lighthouse
gate ≥ 90 mobile per theme in CI; the 120 kB budget unchanged. Console: the customizer page is one client island;
its preview is a separate document, so the editor stays responsive.

**Reliability.** No outbound calls. Autosave retries with backoff and says so; a failed publish leaves the old look
live. Publish and the cache: the publish row commits before `refreshShop`; if revalidation is lost, the 60 s backstop
shows the new look within a minute.

**Security.**
- Actions (`check:actions`): saveDraft, tryTheme, publish, restore, discardDraft, undoPublish, uploadThemeImage — all through
  `asMember` with roles: edit `CAN_BUILD` (owner, admin, partner); publish/undo/restore-live `CAN_MANAGE` and not support.
- Every input Zod-parsed by the version's schema; links only to the shop's own paths; text never rendered as HTML
  (React escapes; the rich-text AST renders known nodes only).
- Images: Blob uploads through the existing signed path, size and type limits, tenant path.
- Preview: members only, the tenant's own revision, `private, no-store`, `noindex`, framed only by the console origin.
- ADR-0003: sections bind to `StoreShop`/`StoreCatalogue` types (no cost fields); Best sellers returns ids only;
  `scripts/check-client-bundle.mjs` still runs.
- Admin (T3): release, recall, withdraw = admin role only; all audited.

**Unit economics.** Themes free in every plan (owner call 2): no new merchant cost. Frrata's costs: Blob for theme
images (small), CI time for screenshots and Lighthouse (minutes per PR), one extra cached read per shop. Upside: the
delivered-order fee on any conversion gain. `unit-economics-reviewer` runs on the plan to check nothing here moves
the margin, and to set the premium smoke-test's success line for T3.

**Blast radius.** Every shop page's shell and Home change in T0 (pixel-identical by the visual gate). Settings' accent
and font section moves to Look in T1 (the console preview and Settings' footer preview use the same shell). The
console preview route and `security-headers.ts` (framing exception). `check:hex` (one new allowed folder). Footguns:
a manifest edited after release (gate + sha in T3); a section changing its settings shape without a migration (the
`check:theme` schema snapshot test); a theme reading a cost field (types + bundle check).
