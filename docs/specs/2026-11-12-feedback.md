# Feedback: toasts, popups and field errors
Status: draft · Date: 2026-11-12 · Mockup: https://claude.ai/artifact/J74M3yUytfbgkMh4UNQbcp (`docs/mockups/2026-11-12-feedback.html`) · Approved: —

## Goal
Owner, 2026-11-12: "always use toasts, popups for errors, validation … with good motion transitions and graphics …
in future we should have these by default." Moves (3) catalogue operations (a merchant sees at once what failed and
how to fix it, without hunting for a red line) and (4) mobile checkout conversion (a shopper's mistake is found and
fixed in one tap; nothing typed is lost). Measure: every error path in the e2e flows asserts a toast or a field error
(no page-top red line left); checkout's "details need fixing" → order placed rate in Analytics.

## Job
When something a person did fails, they see it where they are looking, in the same shape on every screen, with the
one action that fixes it, and it moves the way the rest of Frrata moves.

## The rule (owner-approved in this spec's sign-off; then `frata-design-language` § Feedback)
1. **A failure after a button** (save refused, a conflict, no network, a server refusal, Admin's `?error=`) → a toast
   of kind `error`: ink toast, red mark, one line + optional second line, one action (Try again / Reload / Show) and
   a close ×. It **does not leave by itself**, uses `role="alert"`, and sits above the phone's pay or save bar.
2. **Success** → a toast of kind `ok` (green check), 8 s, Undo where the action is reversible (today's rule).
3. **Field mistakes stay at the field** (red edge + one short line + icon), checked on blur and on submit, cleared as
   soon as the field is fixed; on submit focus moves to the first wrong field and one `error` toast says
   "2 fields need fixing · Show", which counts down as they are fixed and leaves at zero. Nothing typed is cleared.
4. **Popups** confirm what loses work, money or stock (today's rule); a failure inside a popup shows in that popup,
   never a second one. Every popup is the native `Dialog` (the phone sheet), with a small pictogram.
5. **Stays where it is** (rule-pinned): "Pick a size.", a code that doesn't apply, a failed payment's filled form,
   "Price updated to ₹…", a domain's row problem, "Couldn't count", autosave's "Not saved", Publish's blocking list,
   `Panel` load/no-access states, the support-mode banner.
6. **By default**: one app-wide `<Toaster>` per surface (console, Admin, partner, shop) so any island can `toast()`;
   `toast.error()` and `<FieldError>` primitives; a gate `check:feedback` refuses new inline `role="alert"` error
   lines and `?error=` reads outside the primitives (an allow-list for rule 5).

## Research (sources and dates in the research note below)
- W3C WCAG 2.2 (pages updated Jun–Nov 2026): status messages need `alert` for errors, `status` for success (4.1.3);
  the error names the field in text (3.3.1, placement free); a toast that leaves on a timer must carry nothing found
  nowhere else (2.2.1); a toast must not cover the focused control (2.4.11). **Taken:** errors persist; fields keep
  their text; the toast sits clear of the pay bar.
- GOV.UK error summary (Jun 2026): show both a summary and the field errors; move focus. **Taken:** focus moves to
  the first field (our summary is the toast, which never takes focus).
- Baymard checkout audit (13 May 2026): 31% of sites have no inline validation; never clear what was typed.
  **Taken:** rule 3.
- Atlassian Flag (`@atlaskit/flag` code 2026-11-10): never auto-dismiss an error. Material/Flutter (Sep 2026): a
  snackbar with an action persists; one at a time. Razorpay Blade (code 2026-11-06, docs 2026-10-29): error toast
  `negative`, no auto-dismiss, Retry; critical errors use an alert or modal; one toast on a phone. Shopify app
  guidelines (undated, unverified): avoid toasts for errors except persistent ones like connection; avoid modals for
  errors. **Taken:** rules 1, 4.
- Motion: Pope Tech (Dec 2025) — a shake is never the only signal; MDN (Jun 2026) — replace movement with a fade under
  reduced motion. **Taken:** no shake; our existing 200 ms toast/dialog motion, 320 ms phone sheet, and a 200 ms icon
  pop on `--ease-snap`; reduced motion: a 120 ms fade.

## Design (mockup)
Views: Toasts (five kinds), Console form (two mistakes, a server refusal, saved), Admin (today's red line vs the

## Inventory (scan 2026-11-12)
148 sites: console 89, Admin 27 (19 pages of `?error=` lines from ~60 redirects, plus browser `required` bubbles),
shop 17, EkCode 5, sign-in 8, partner 2. Five already use the toast. Bugs found: Share sheet's QR failure is green
`role=status`; EkCode's "locked" line has no `role=alert`; the customizer's hand-made toast has no exit or pause;
`LeaveDialog` is a div, not the native `Dialog`.

## Phases (each a merchant can use alone)
- **F0 Primitives** — `toast` kinds (`ok`, `error`), persistent errors, `role` by kind, app-wide Toaster per surface,
  `FieldError` + `useFieldErrors` (focus first, summary toast), `Dialog` inline error slot, `LeaveDialog` → `Dialog`,
  the customizer's toast → `ui/toast`; gate `check:feedback`; e2e for each primitive. Regression net first: the
  e2e flows that assert today's error lines.
- **F1 Console** (89 sites) — action failures and network → error toast; fields → F0 field errors.
- **F2 Admin** (27) — `?error=` read once into a toast (then removed from the URL); `required` bubbles → field errors.
- **F3 Shop, EkCode, sign-in, partner** (32) — shop toasts in the shop's own colours; checkout keeps its rule-pinned
  blocks.

## Design review
- **UI/UX** — one primitive per job; feedback after every action; recognition (the field is marked) over recall (a
  toast that left); Undo kept; keyboard: the toast's action and × are reachable, Esc closes an error toast; phone:
  above the pay bar, 16 px gutters.
- **Tenancy** — n/a: no data, no queries.
- **Modularity** — primitives in `src/components/ui/`; the shop's in `src/components/storefront/`; no engine change.
- **SSOT / DRY** — the words stay where they are produced (actions return `{ error }`); one toast, one Dialog.
- **YAGNI** — no stacked toasts (one at a time, as today); no toast history; no shake.
- **KISS** — CSS motion already in `base.css`; no library (rule 22).
- **Scalability / performance** — client only; the Toaster is a small island per surface (bundle check in F0).
- **Reliability** — n/a (no calls).
- **Security** — `?error=` text is never rendered from an arbitrary URL: Admin reads a known code or a short string
  its own action set (F2 replaces free text with codes).
- **Motion and visuals** — § Motion patterns only (200 ms toast/dialog, 320 ms sheet, `--ease-snap` icon pop);
  pictograms on popups from § Graphic language; reduced motion fades.
- **Unit economics** — n/a.
- **Blast radius** — every form and action result in four surfaces; e2e assertions on error text move with it.

## Out of scope
Stacked toasts (signal: two failures at once lose one in practice); a notification centre (signal: owners ask what
they missed); sound or vibration.
