# P3·1 spike: the phone test script
Status: ready to run (prepared 2026-11-22, lane E) · Plan: `docs/plans/2026-11-16-one-address-checkout.md` § P3 (P3·1) and § Integration
facts · Spec: `docs/specs/2026-11-16-one-address-checkout.md` § 2, § 2b · Mockup (states): https://claude.ai/artifact/VAND3HpPwsd5MvkjBuWnFA

This is the script for **one person with an iPhone and an Android phone** to run the six pass/fail lines (a)–(f) of
the P3·1 spike, tap by tap, and record what happened. Nothing here is built yet. An engineer sets up the test pages first
(§ 1). The person then runs § 3 to § 8 and fills in the sheet (§ 9). The owner reads the dated report that comes out of
it, and P3 starts only once it passes.

## 0 · What the spike decides
| Line | Pass | If it fails |
|---|---|---|
| (a) | Razorpay Checkout opened **from inside the secure frame** completes a payment by UPI intent, card and netbanking in Android Chrome and iPhone Safari. In Instagram's in-app browser it completes UPI intent and cards only, because Razorpay's netbanking page never shows there, framed or not (integration fact, 2026-11-16). WhatsApp's in-app browser is tested the same way as Instagram's. | Razorpay opens from the page instead, with the shopper's contact held in memory only (decision 15). |
| (b) | EkCode's popup returns to the frame by `postMessage`, sent to the exact store origin, in all the browsers tested. | When no popup handle comes back, the fallback runs: the same tab goes to ekcode.in and back to `/checkout` (today's path). It is planned already, and the spike records which browsers need it. |
| (c) | The frame's `__Host-` cookie is still there after a day in WebKit (iPhone Safari and iPhone in-app browsers). On a brand domain it is still there on day 8. | The frame's state moves to tab storage, or the shopper signs in again. P3·7 decides, with `security-reviewer`. |
| (d) | Vercel issues certificates for `secure.<store>.frrata.shop` and `secure.<brand domain>`. | P5·7 waits, and the 40-a-week queue is planned. |
| (e) | COOP `same-origin` (or `same-origin-allow-popups`) severs a partner page's handle to checkout in each browser tested. | Decision 20 (approved): no partner JavaScript in those browsers (C5). This is **expected on Android in-app browsers**, because Android WebView does not support COOP (integration fact, 2026-11-16). |
| (f) | A cold checkout with the frame, on a mid-range Android phone over 4G, is within **300 ms** of today's checkout at p75. | The frame's bytes and statements are cut (P3·6's budgets) before P3 ships. |

## 1 · Before the phones (an engineer, about a day)
None of this goes to production. It goes on a **preview deployment** of a throwaway branch (`claude/p3-spike`), against
a **spike store** in the test Supabase data, never House of Ayuda's live store.
1. **`integration-researcher` first** (plan P3·1). Recheck the 2026-11-16 facts: Razorpay in a frame, COOP in Android
   WebView, WebKit's 7-day cap, Instagram netbanking. Add Razorpay's current test-mode payment details (test card, test
   netbanking bank, whether test mode shows the UPI app list), each with its date and source. Send **Razorpay the written
   question** (plan § Integration facts): is Checkout inside a frame supported, and does a key work from
   `secure.<host>` when only `<host>` is registered?
2. **Hosts:** the spike store at `spike-p3.frrata.shop`, and `secure.spike-p3.frrata.shop` added to the `frata` project.
   For (c) day 8 and (d), add a brand domain the owner controls (any cheap domain) with `secure.` on the **same record
   type** as the host (A for an apex, the same CNAME for `www`; integration fact on WebKit's CNAME cap).
3. **Test pages** (throwaway, on the spike branch only). Each prints its result in large words on screen, so the person
   only has to read and screenshot:
   - `https://spike-p3.frrata.shop/spike/frame` · a store page that frames `https://secure.spike-p3.frrata.shop/spike/pay`.
     The frame has the `allow="payment; otp-credentials; clipboard-write; web-share"` attribute and a **Pay ₹1** button
     that opens Razorpay Checkout from inside the frame. On success it shows **PAID · <payment id>**, on failure
     **FAILED · <reason>**.
   - `https://spike-p3.frrata.shop/spike/page-pay` · the fallback: the same ₹1 payment opened from the page itself.
   - `https://spike-p3.frrata.shop/spike/ekcode` · the frame with **Continue with EkCode**. It opens the EkCode
     sign-in as a popup and shows **RETURNED IN FRAME** when the popup's message reaches it from the exact origin, or
     **NO POPUP HANDLE · FALLBACK** when `window.open` gave nothing back.
   - `https://spike-p3.frrata.shop/spike/cookie` · the frame sets `__Host-spike` (HttpOnly, Secure, SameSite=Lax,
     Max-Age 30 days) on its first visit. Every later visit shows **COOKIE SET <date, time> · AGE <hours>** or
     **NO COOKIE**.
   - `https://spike-p3.frrata.shop/spike/opener` · a "partner" page with **Open checkout**. It opens
     `https://secure.spike-p3.frrata.shop/spike/coop` (sent with COOP `same-origin-allow-popups`), then after 3 s tries
     to read the checkout window. It shows **HANDLE SEVERED** or **HANDLE OPEN · <what it could read>**. A second
     button does the same against a COOP `same-origin` page.
   - `https://spike-p3.frrata.shop/spike/speed?v=today` and `?v=frame` · today's checkout, and the checkout with the
     frame. Each reports its navigation timing to a log row (device, browser, network type, TTFB, FCP, LCP, the frame's
     load) and shows **LOGGED #n**.
4. **Razorpay:** the spike store's test keys. If test mode does not show the UPI app list (step 1 says), the UPI intent
   step needs a live key and one ₹1 payment, refunded the same day. That is the owner's call (§ 10, question 1).
5. **(d) is checked by the engineer, not on the phones:** `curl -sI https://secure.spike-p3.frrata.shop/` and the brand
   domain's `secure.` both answer over TLS with a certificate for that exact name (`openssl s_client -servername …`).
   Record the dates issued.
6. Send the person: the six links, a QR code for each, and this file.

## 2 · What the person needs
- An **iPhone** (iOS version noted) and an **Android phone** (model and Android version noted; for (f), a mid-range
  phone, like a Redmi, Samsung A-series or Moto G, not a flagship).
- Instagram and WhatsApp installed and signed in on both phones.
- A UPI app on each phone (GPay, PhonePe or Paytm) with a bank linked. It is only used if § 10 question 1 says live.
- The Razorpay test details from § 1 step 1: the test card number, and the test bank's name for netbanking.
- 4G for (f): Wi-Fi **off**, mobile data on.
- 60–90 minutes on day 1, 10 minutes on day 2, 10 minutes on day 8.

**The six browsers.** Run each test in every browser below. The plan names four (Android Chrome, iPhone Safari,
Instagram's and WhatsApp's in-app browsers). In-app browsers differ between iOS and Android, so both phones run both apps.
| # | Phone | Browser | How to open a link in it |
|---|---|---|---|
| B1 | Android | Chrome | Scan the QR code with the camera, or paste the link into Chrome. |
| B2 | Android | Instagram in-app | Send the link to yourself in an Instagram DM (from a second account, or "Send to" your own close-friends chat) and tap it inside Instagram. |
| B3 | Android | WhatsApp in-app | Send the link to "Message yourself" in WhatsApp and tap it. |
| B4 | iPhone | Safari | Scan the QR code with the camera. |
| B5 | iPhone | Instagram in-app | As B2. |
| B6 | iPhone | WhatsApp in-app | As B3. |

**Every time you open a link in an app, check which browser it really opened in.** An in-app browser shows the app's
own bar (Instagram's or WhatsApp's) at the top, often with the site's address and a ⋯ menu. If the link opened in Chrome
or Safari instead, write that in the sheet. That outcome is a result, not a mistake.

**Screenshots:** take one at every result screen. Name them `<line>-<browser>-<step>`, for example `a-B5-card.png`.

## 3 · (a) Razorpay from inside the frame
Run in **each browser B1–B6**.
1. Open `…/spike/frame`. You see the store page with a framed box and **Pay ₹1**.
2. **Card:** tap **Pay ₹1** → Razorpay opens. Choose **Card** → enter the test card from § 1 → **Pay** → follow the
   test bank's page and tap **Success**. Record what the frame shows (**PAID** or **FAILED**). Screenshot.
3. Reload. **Netbanking:** **Pay ₹1** → **Netbanking** → the test bank → **Success**. Record. In B2 and B5
   (Instagram), write down whether Netbanking was offered at all. It is expected to be missing.
4. Reload. **UPI intent:** **Pay ₹1** → **UPI** → do you see your UPI apps listed (GPay, PhonePe…)? Record yes or no.
   - If yes: tap your app. Does the app open? If § 10 question 1 says live, approve the ₹1 and come back to the
     browser. Record whether the frame shows **PAID**, and whether you came back to the same page.
   - If no (only a QR code or a UPI ID box): record "no intent list".
5. **Only if any of 2–4 failed in this browser:** open `…/spike/page-pay` and repeat the failed step. That tells us
   whether the fallback works there.

**Pass (a):** B1 and B4 PAID by card, netbanking and UPI intent. B2, B3, B5 and B6 PAID by card and UPI intent (netbanking
may be missing). Anything else is a fail for that browser.

## 4 · (b) EkCode's popup back to the frame
Run in **each browser B1–B6**.
1. Open `…/spike/ekcode` → tap **Continue with EkCode**.
2. Write down what happened: a new window or tab opened (popup), or the **same** tab moved to EkCode.
3. Sign in with your phone number (the code comes on WhatsApp). Finish.
4. Record the final screen: **RETURNED IN FRAME** (pass), **NO POPUP HANDLE · FALLBACK** (the fallback ran: record it
   and whether you ended back on the spike page signed in), or anything else (fail, screenshot it).

**Pass (b):** RETURNED IN FRAME in every browser. NO POPUP HANDLE with a working fallback is an expected result in
Android in-app browsers (integration fact). Record it, but don't count it as a pass of the popup.

## 5 · (c) The frame's cookie over a day, and day 8
Run in **B4, B5, B6** (WebKit). Run in B1–B3 too if there is time; it is cheap.
1. **Day 1:** open `…/spike/cookie`. First visit: it shows **COOKIE SET <time>**. Note the time. Close the tab. Don't
   clear anything.
2. **Day 2, at least 24 h later:** open the same link the same way (Safari directly; for Instagram and WhatsApp, tap the
   same message again). Record **COOKIE SET <same time> · AGE ~24 h** (pass) or **NO COOKIE** (fail).
3. **Brand domain:** on day 1, also open `https://<brand domain>/spike/cookie` in B4. On **day 8**, open it again in B4
   and record. This is WebKit's 7-day cap on a subresource whose CNAME differs; it should hold because `secure.` sits on
   the same record type.

**Pass (c):** the cookie is there on day 2 in B4–B6, and on day 8 on the brand domain in B4.

## 6 · (d) Certificates
The engineer checks this (§ 1 step 5), not the person. Record in the sheet: each `secure.` host, the date its
certificate was issued, and its issuer.

**Pass (d):** both hosts answer with a valid certificate for their exact name.

## 7 · (e) COOP severs a partner page's handle
Run in **each browser B1–B6**.
1. Open `…/spike/opener` → tap **Open checkout (same-origin-allow-popups)**. A checkout page opens (new tab or window).
2. Go back to the opener tab (tab switcher, or the in-app browser's back). Wait for the result: **HANDLE SEVERED**
   (pass) or **HANDLE OPEN · …** (fail; screenshot it, it shows what it could read).
3. Repeat with **Open checkout (same-origin)**.

**Pass (e):** HANDLE SEVERED in every browser for at least one of the two values. If B2 and B3 (Android in-app) show
HANDLE OPEN, decision 20 applies to them, as planned. Record it plainly; it is the expected outcome.

## 8 · (f) Speed: a cold checkout with the frame over 4G
Run on the **Android phone, B1 (Chrome)**, Wi-Fi off, mobile data on. Note the signal bars and the network (4G / 5G).
1. Open a **new incognito tab** (Chrome ⋮ → New incognito tab), so each load is cold.
2. Open `…/spike/speed?v=today`. Wait for **LOGGED #n**. Close the incognito tab.
3. New incognito tab → `…/spike/speed?v=frame` → **LOGGED #n** → close.
4. Repeat steps 1–3 until each has **20 loads**, alternating today and frame. This takes about 15 minutes.
5. The engineer reads the log and computes p75 of LCP and of "checkout ready" (the frame loaded) for each.

**Pass (f):** p75(frame) − p75(today) ≤ 300 ms. The report also records p95 and the first, coldest load.

## 10 · Questions for the owner before the run
1. **UPI intent with a live key?** Razorpay test mode may not list UPI apps. Proving intent end to end then needs the
   spike store's live key and one ₹1 payment per browser (up to six ₹1 payments), refunded the same day.
   Recommendation: yes, on the spike store only. Otherwise (a)'s UPI line stays unproven until the pilot.
2. **A brand domain for (c) day 8 and (d):** a cheap domain the owner registers for the spike, or one already owned.
   Recommendation: a new cheap one, dropped after the spike.
3. **Who runs it:** anyone with the two phones. It needs no console access. The engineer needs about a day before it
   and an hour after.
