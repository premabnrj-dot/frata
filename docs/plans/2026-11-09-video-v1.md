## Goal
North star (5) a premium-looking storefront: a short muted loop in a Hero or an Image with text, the way design-led D2C
sites move. Measure: share of Signal shops with a published loop after 30 days; the shop page's LCP unchanged (the
section's photo stays the first paint, the video fades in over it).

## What a merchant does (the approved board)
In a Hero or Image with text: **Add a video** (MP4 or MOV, up to 15 s) → **Uploading** (progress, Cancel) → **Getting
it ready** → **Ready** (poster, length, Replace, Remove); **Didn't work** (Choose another). Also: video not switched on
(no Mux env), a support visit and a role without CAN_BUILD (read-only), a phone (a MOV from the camera roll). The shop
plays it muted, on loop, only in view, one loop at a time, with no sound and no player bar. With no video, the photo
shows, as today.

## Decisions taken from the reviews
- **No CSP change** (arch blocker 1, security 4). Today's policy has no `img-src`/`media-src`/`connect-src`, so nothing
  is blocked; adding one host would block every Blob photo, Supabase and RSC fetches. The server instead checks the
  upload URL Mux returns is `https://` before replying. Locking origins down is its own task later.
- **No Mux in Preview** (arch 2, security 2): previews share the production database and the outbox. `MUX_*` are
  Production only until Preview has its own database. Every row carries `mux_env` (the environment id from config);
  the webhook refuses an envelope whose environment differs; the delete sender defers a row from another environment
  and counts 404 as done only when the environments match.
- **Cost caps** (unit economics; security 1): video on every plan; `max_resolution_tier: 720p`; clips ≤ 15 s (checked
  on ready, longer ones errored `too_long` and deleted); one loop playing at a time; uploads started per shop capped in
  every state: 10 a day, 30 a month (trial shops 3 a day); a platform-wide hourly cap, fail closed; Mux upload
  `timeout` 900 s; the 20-live-video cap counted under a per-shop advisory lock. A monthly delivered-minutes budget
  per shop waits on a verified Mux usage API (integration-researcher) and the replay-billing test in the development
  environment.
- **Every Mux call from the server is a row first**: create upload is ADR-0008 (attempt row, then the call); deletes
  (Remove, a too-long asset, an asset that lands on a removed or errored row, a cancelled upload) are outbox
  `mux.asset.delete` / `mux.upload.cancel` in the same transaction, never from `after()`. The delete reads `asset_id`
  from the row, never from a request.
- **Draft-safe Remove/Replace** (arch 5): they only detach the video from the draft. `removed_at` and the delete go out
  at publish or discard, for videos neither the live revision nor the draft references. The 20 cap counts referenced
  or pending videos.
- **State derived at read time** (arch 4): pending with no `upload_id` after 2 min, or no `ready_at` after the upload
  timeout + 10 min, reads as "Didn't work". The daily net gains `shopsWithPendingEvents('mux')`.
- **The console learns "ready"** by a status read polled with backoff (2, 4, 8 … 30 s) while a video is pending, stopping
  at ready or errored; the state is derived from the row, so a reload shows the same.
- **LCP** (arch 7): the section's photo stays the first paint (it is already preloaded); the `<video>` lies over it and
  fades in on `playing`. The Mux thumbnail is used only when the section has no photo (then preloaded, lead section
  only). `prefers-reduced-motion` or `saveData`: the photo/poster only.
- **Webhook routing tight** (security 3): the definer needs a `passthrough` uuid **and** an `upload_id` equal to the
  row's (a pending row with a null `upload_id` takes it from the event once); fields regex-checked; known event types
  only; returns the tenant id only; stores `{type, id, upload_id, asset_id, status}` only (never the upload URL),
  trimmed to `{type}` once processed; revoked from public, anon, authenticated, service_role. The processor checks the
  fetched asset's `passthrough` and `upload_id` against the row before writing; writes no `playback_id` when too long.
  Route listed in ENTRY_POINTS. Two webhook secrets accepted during a rotation.
- **The shop sees only published videos** (security 7): the publishes cache entry (`publishes-v2`) carries id →
  playback id and width/height for videos the live look references; playback ids checked `^[A-Za-z0-9]{1,64}$`,
  sizes bounded. The shop's tag is refreshed only on the transition to playable or removed.
- **Columns** (arch minor): `upload_started_at` dropped (`created_at`); `width`/`height` integers, not `aspect`.
  `frata_app` updates named columns only, no delete. `allowed.videoSections?: SectionKey[]` (a list, so S2's Spotlight
  fits), with `video: null` narrowing and a carryOver "video isn't in X" line; a new stored-sections fixture.
- **Save check**: `cleanVideos(tx, layer, tenantId)` in `src/lib/queries/` called from `saveLookAction`; another shop's
  id is refused.
- **Fake Mux**: `MUX_API_BASE` (refused in production unless `https://api.mux.com`) and a stream/image base for e2e.
- **Spec fix**: no "outbox token bucket" exists; uploads use the ADR-0008 path.
- Known gaps, accepted: the 64 MB cap is browser-only (the duration check and the per-day caps bound the cost); a shop
  deleted with queued deletes leaves assets at Mux (Admin can remove a video; a sweep comes with shop deletion).

## Design
- **Not a module.** Part of the section library, offered only by themes whose manifest lists the section in
  `allowed.videoSections` (Signal: hero, image_text).
- **Table `videos`** (per shop): `id`, `tenant_id`, `mux_env`, `upload_id`, `asset_id`, `playback_id`, `duration_ms`,
  `width`, `height`, `created_at`, `created_by`, `ready_at`, `mp4_ready_at`, `errored_at`, `error` (≤ 40), `removed_at`.
  State derived from timestamps. Grant (named columns), RLS, policy, tenancy.sql: A can't read or update B's rows; a save
  naming B's id is refused. Unique `upload_id`, `asset_id`.
- **Start an upload** (`startVideoUpload`, CAN_BUILD, support visits refused, Zod `{contentType: mp4|quicktime, size ≤
  64 MB}`, limits per member, per shop (day, month), platform hour, fail closed): row committed, then `POST
  /video/v1/uploads` (fetchWithTimeout) with `cors_origin` = console origin, `new_asset_settings` {passthrough: row id,
  playback_policies: public, video_quality: basic, static_renditions: [highest], max_resolution_tier: 720p}, `timeout`
  900; reply `{videoId, url}` only.
- **The browser uploads straight to Mux** (PUT with progress). Cancel aborts the PUT and queues `mux.upload.cancel`.
- **Webhook** `/api/webhooks/mux` (ADR-0006): `content-length` ≤ 1 MB checked before reading, `mux-signature` on the raw
  body (HMAC-SHA256 over `t.body`, 5-min tolerance, constant-time), stored under `mux:<env>:<envelope id>` through the
  definer; 200 at once; processed in `after()` by GETting the asset.
- **The shop plays** `<video muted loop playsinline preload="none">` over the section's photo, `src` =
  `https://stream.mux.com/{pid}/highest.mp4` (720p) set by one island only in view; one playing at a time; no player.
