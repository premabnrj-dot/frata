# EkCode P1 — sign-in on shops, the vault, ekcode.in, Admin controls
Status: built, e2e running (owner "now execute", 2026-11-09; reviewed by tenancy, security, architecture, speed, unit economics) · Date: 2026-11-09 · Spec
`docs/specs/2026-11-09-shopper-login.md` (active) · Mockup https://claude.ai/artifact/A33Xi8HVfsAyZqQ2pn7uKu (v4, approved)
· ADR-0008, ADR-0009, ADR-0010 · Review notes § Findings at the end.

## Goal
North star (4) checkout conversion and (1) COD/RTO: a shopper with EkCode is filled in on any shop with one WhatsApp
code; every EkCode sign-in proves the phone RTO Shield scores. **Measures from day one**: checkout completion with vs
without EkCode (holdout pooled across shops), share of orders from a checked phone, RTO on checked vs unchecked COD.
Unit economics: EkCode pays for itself at a checkout lift of ≥ 2.1% (Launch) / 3.0% (Growth) / 4.6% (Scale).

## Owner calls this plan needs (recommendations applied; the owner may reverse)
1. **No email code** (owner confirmed, 2026-11-09; security C1 / architecture blocker): an email code proves an email, never a phone, so it
   must not open or create an account keyed by the phone — otherwise anyone can type a stranger's number, take the
   code by email and read their name and addresses. P1 ships WhatsApp only; a shopper whose code doesn't arrive gets
   "Resend" and "Check out as a guest". **Owner, 2026-11-09: no email in EkCode until SES is connected and planned**;
   the mockup's email screens wait for that plan.
2. **Per-shop codes a day: Launch 100, Growth 600, Scale 2,000** (Admin raises one shop) instead of 500 / 2,000 /
   6,000 — caps Frrata's worst month at ₹345 / ₹2,070 / ₹6,900 (unit economics).
3. **Abuse slows down, it doesn't switch a shop off**: past the 2nd code an hour from one network the browser solves a
   small proof of work (no outside vendor); the breaker raises that difficulty and tells Admin — only Admin pauses a
   shop (security H4: otherwise anyone could switch off a competitor's EkCode).
For P3 (recorded in the spec, not built here): order-update allowance = the larger of 600 / 6,000 / 20,000 and 4 ×
orders placed this month; COD confirmation never pauses.

**7 · The handshake (shop ⇄ ekcode.in)** (tenancy B1, B2, M2, M3, M5; security H3, M1, M6; speed M1, M3)

- `GET /api/shop/ekcode/return`: state compared timing-safe and the cookie cleared; in **one** `withTenant` transaction

  token; 303 to `/checkout#ek`. Invalidates no cache tag.
- `GET /api/shop/ekcode/me` (a GET variant of `shopRequest`: `requireShop` + limit, no body): called only on `#ek` or

## Practices recorded in skills (same commits)
- **Architecture**: a platform table outside every tenant has no grant and a restrictive false policy; definers take
  their scope from a server-made handle, never an argument a caller chooses; pairwise ids are random rows, deletable.
- **Security**: PKCE handshake with the return URL built from the database; one-time grant codes stored as hashes; the
  same reply whether an account exists; proof of work instead of a challenge vendor.
- **Speed**: brand marks as server components passed into islands; an island calls its API only when there is
  something to read.
- **Testing**: an e2e fake per outside service the flow touches.
