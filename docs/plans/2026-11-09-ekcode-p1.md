# EkCode P1 — sign-in on shops, the vault, ekcode.in, Admin controls
Status: draft (reviews running) · Date: 2026-11-09 · Spec `docs/specs/2026-11-09-shopper-login.md` (active) · Mockup
https://claude.ai/artifact/A33Xi8HVfsAyZqQ2pn7uKu (v4, approved 2026-11-09) · ADR-0008, ADR-0009, ADR-0010

## Goal
North star (4) checkout conversion and (1) COD/RTO: a shopper who has EkCode is filled in on any shop in one code; every
EkCode sign-in proves the phone RTO Shield will score. **Measures from day one**: checkout completion with vs without
EkCode (1 in 10 checkout visits held out), share of orders from a checked phone, RTO on checked vs unchecked COD.

## What P1 ships (and what waits)
Ships: ekcode.in (home, Privacy, Terms, Contact, `/continue`); phone → WhatsApp code → (first time) Create → Continue to
the shop → back, filled; email code when WhatsApp fails; Not now; Not you?; "Save this address to EkCode" (ticked,
owner); the shop's first-party session; the vault and its definers; Console › Apps › EkCode row with its switch and
Settings (show at checkout, holdout); Admin › EkCode Overview, Shops, Controls (switches, limits, breaker, blocks).
Waits: P2 — remembered phone and "Continue as" one tap, the shopper's EkCode page, Apps Overview and Shoppers (leads,
export), Admin Privacy (requests, lookup, notice versions). P3 — order updates from EkCode's number (rides M·1's
`whatsapp.send`, ADR-0010), the allowance meter, Admin WhatsApp.

## Tasks (each ends with its verify command, read, and `impact-reviewer` on its diff before commit)

**1 · Pure rules — `src/domains/ekcode/`** (no I/O; `check:layers`)
- `phone.ts`: `indianMobile` moves here from `src/lib/trials/signup-code.ts` (one copy; sign-up imports it).
- `flow.ts`: a sign-in attempt's state derived from its timestamps (started, number_in, code_sent, delivered,
  verified, account_created, continued, abandoned) — no status column; `nextStep(flow, now)` and the email offer
  (131026 at once; no `delivered` 20 s after `code_sent`).
- `limits.ts`: the limits as data (3 codes / number / 10 min; 5 tries / code; 20 codes / network / hour; per-shop codes
  a day by plan 500 / 2,000 / 6,000; breaker: < 40% right after 200 codes in 24 h) and `verdict(counts, settings)` →
  allow | wait(until) | locked(until) | breaker.
- `notice.ts`: the notice text v1 (English, owner), its version, the items shared; `shareItems(choice)`.
- `holdout.ts`: `armFor(visitorId)` → 'shown' | 'held' (1 in 10, stable per visitor id; no fingerprint).
- `brand.ts`: the copy strings shoppers read (one place, so the brand gate can check it).
- Verify: `npx vitest run src/domains/ekcode` (each rule with its edge cases) · `npm run check:layers`.

**3 · The vault — migration 0085 `ekcode` (+ custom 0086 RLS, grants, definers)**
- Platform tables (no `tenant_id`; RLS on, **no policy, no grant to `frata_app` or `frata_admin`**; definers only):
  `ekcode_accounts` (id, phone_hmac unique, phone_sealed, name_sealed, created_at, deleted_at),
  `ekcode_addresses` (account, label, sealed address, last_used_at, deleted_at), `ekcode_consents` (account, kind
  `network`|`share:<pairwise>`, notice_version, given_at, withdrawn_at), `ekcode_disclosures` (account, pairwise id,
  items, at), `ekcode_codes` (id, phone_hmac, account null, channel, code_hmac, sent_at, delivered_at, failed_code,
  tries, expires_at, tenant, ip_hash, flow), `ekcode_flows` (id, tenant, arm, timestamps of § flow.ts; no phone),
  `ekcode_grants` (code_hmac, flow, account, tenant, return host, challenge, items, address id, expires_at, used_at),
  `ekcode_settings` (one versioned row: switches, limits), `ekcode_blocks` (phone_hmac or ip prefix hash, reason, by,
  at, lifted_at).
- Tenant tables (grant, RLS, policy in the same migration; `check:tenant`): `shop_customers` (tenant, id, pairwise_id,
  phone, name, first_seen, source; unique (tenant, pairwise_id)), `customer_sessions` (tenant, customer, token_hash,
  prefill_sealed, prefill_expires_at, expires_at, revoked_at), `customer_consents` (tenant, customer, purpose
  `order_updates`|`marketing_whatsapp`|`marketing_email`, sender `shop`|`ekcode`, notice_version, given_at,
  withdrawn_at) — shaped for M·1 too (ADR-0010). `orders.ekcode_arm` (null | shown | held) and `orders.customer_id`.
- Definers (SECURITY DEFINER, `search_path` pinned, each re-checks its proof; granted to `frata_app` only where
  named): `ekcode_start_flow(tenant, arm)`, `ekcode_issue_code(flow, phone_hmac, channel, code_hmac, ip_hash, now)` →
  code id or a limit verdict (the ADR-0008 attempt row, committed before the send), `ekcode_mark_sent/failed`,
  `ekcode_verify_code(code id, code_hmac, now)` → a single-use proof (5 tries, 10 min), `ekcode_create_account(proof,
  phone_sealed, name_sealed, notice_version)`, `ekcode_account_view(proof)` → name, masked phone, address labels
  (never full addresses), `ekcode_grant(proof, tenant, return_host, challenge, items, address id, save_address)` →
  one-time code (60 s), `ekcode_redeem(code_hmac, verifier, tenant)` → pairwise id + the confirmed items, writes the
  disclosure and the share consent; `ekcode_save_address(...)` (the ticked box, after the order). Admin (`frata_admin`,
  admin role re-checked): `ekcode_admin_stats(period)`, `ekcode_admin_shops(period)`, `ekcode_admin_set(settings,
  reason)`, `ekcode_admin_block/unblock(…, reason)`, `ekcode_admin_pause_shop(tenant, reason)` — aggregates only.
- Proofs added to `scripts/verify/tenancy.sql`: `frata_app` cannot select any `ekcode_*` table; a proof for phone A
  cannot read account B; a used proof or grant is refused; a grant for shop A cannot be redeemed by shop B; shop B
  sees no `shop_customers` of A; `frata_admin` gets counts, never a name, phone or address.
- Verify: `npm run db:generate` (no drift) · `npm run check:tenant` · `npm run verify:tenancy` (throwaway Postgres) ·
  `npx vitest run src/lib/ekcode --project int`.

**4 · Senders — `src/lib/ekcode/send.ts`**

**5 · Webhook — `/api/webhooks/ekcode`**
- GET verify (`EKCODE_WA_VERIFY_TOKEN`); POST verified on the raw body (`EKCODE_META_APP_SECRET`), size-capped,

**6 · The ekcode.in host**
- `routeFor` learns `{ kind: 'ekcode' }` for `EKCODE_HOST`; next.config rewrites it to the route group
  `src/app/ek/…`; `/ek/…` is a 404 on every other host (as `/s/` is). Its own strict CSP (no third-party script),
  `X-Frame-Options: DENY`, HSTS, no Supabase session work.
- Pages: `/` (home), `/privacy`, `/terms`, `/contact` (static, cached), `/continue` (static shell + one client island;
  all calls to `/api/ek/*` on the same host, `no-store`).
- Cookie: `__Host-ek_flow` (HttpOnly, Secure, SameSite=Lax, 15 min, signed flow id + proof handle). Nothing else.
- Verify: `npx vitest run src/domains/tenancy` (host table) · e2e 12-security: `/ek/` refused on a shop and the
  console; ekcode.in pages carry the headers.

**7 · The handshake (shop ⇄ ekcode.in)**
- Shop route `GET /ekcode/start` (no-store): a random `state` and PKCE `verifier` in `__Host-ek_state` (HttpOnly,
  10 min), 302 to `https://<EKCODE_HOST>/continue?shop=<host>&state=…&challenge=S256(verifier)`.
- ekcode.in accepts only a live shop host with EkCode on (`tenantForHost` + module usable); the return URL is always
  `https://<that host>/ekcode/return` — never taken from the query (no open redirect).
- After Continue, ekcode.in 302s to `/ekcode/return?code&state`; the shop checks `state` against its cookie, redeems
  with the verifier, upserts `shop_customers`, opens `customer_sessions` (`__Host-shop_s`, HttpOnly, Secure, Lax, 30
  days), seals the prefill (24 h), and 303s to `/checkout`.
- `/api/shop/me` (no-store, `shopRequest`) returns the prefill to the checkout island; cached shop pages never read the
  cookie. "Not you?" revokes the session.
- Verify: e2e 67 (open redirect, state mismatch, replayed code, another shop's code) · unit tests of `pkce.ts`.

## Practices recorded in skills (same commits)
- **Architecture**: a platform table outside every tenant has no grant to any app role; definers re-check a proof;
  pairwise ids per shop. A second public host (ekcode.in) is a `routeFor` kind with its own route group and CSP.
- **Security**: the PKCE handshake and fixed return path as the pattern for any cross-host return.
- **UI**: `frata-design-language` § EkCode (already recorded, 5.11.0).
- **Testing**: an e2e fake per outside service the flow touches (Meta EkCode number, SES).
