## Goal and measure
Ranked problem 5 and 7 (a premium storefront built as code; festive-peak reliability): the move must break no store address,
no key and no checkout. Measure: after the flip, every `<store>.frrata.shop` URL answers a 308 to the same path on
`<store>.frrata.store`, every released `api.frrata.shop` URL answers as before, and the e2e flows below pass on both.

## The owner's decisions (2026-11-24)
1. "We need to replace frrata.shop with frrata.store (I can renew this for 3 years)": a store is `<store>.frrata.store`,
   the Storefront API `api.frrata.store`.
2. "preview domain can be: frratapreview.store (can buy for 3 years)": the separate registrable preview domain (ADR-0019
   point 8, O6).
3. "public domain can be frrata.shop": Frrata's own public site. This reverses ADR-0019's context line (frrata.com public).

## The order: no store address breaks at any step
Each step ends with a check; the next starts only when it passes. Nothing changes a live address until step 3.
1. **Code, dark (a release with no behaviour change while the new settings are unset).** Items 6–11, 13, 15, 16: the legacy
   domain and the API alias are read from new variables that are empty, so production behaves as today. Gates, unit tests and the e2e
   flows below. Docs and kit text are changed in step 5, not here.
2. **Provider, nothing links to it yet.** The owner renews `frrata.store` (3 years) and buys `frratapreview.store`; nameservers to
   Vercel; add `frrata.store`, `*.frrata.store`, `api.frrata.store` to the `frata` project; wait for the wildcard certificate.
   Check: `curl -sI --resolve` against the project's address for a test store on the new host answers; the old hosts are unchanged.
3. **The flip, one release, off-peak and outside any sale.** Set `NEXT_PUBLIC_SHOP_DOMAIN=frrata.store`, the legacy domain
   `frrata.shop`, `NEXT_PUBLIC_API_HOST=api.frrata.store`, the legacy API host `api.frrata.shop`; redeploy (public values are built in).
   From here every derived address (console, emails, sitemaps, canonicals, the API's `shop.siteOrigin`) is new; an old store host answers a 308,
   an old API host answers as before. Firewall rules (item 14) updated the same hour. Check: the curl matrix below.
4. **The agent.** Item 12: new environment and agent version allowing both API hosts, a vault credential for the new host, then
   `STUDIO_*` ids in Vercel; later a version allowing only the new host, once sessions on the old version have ended (retention is 30 days).
5. **Published words.** OpenAPI `servers`, the docs, `llms.txt`, the kit, the skills, `CLAUDE.md`, `docs/setup.md` (item 10, 13, 24).
   Tell partners (their code keeps working through the alias).
6. **The listing.** Open the Public Suffix List request for `frrata.store` (item 19); `__Host-` cookies are already the rule, so nothing
   waits on it. After it lands, run `check:cookies` and the cross-store flow again.
7. **The public site on `frrata.shop`.** Separate work, not in this plan: until a public site exists the bare `frrata.shop` keeps its 307 to the console
   host (`src/middleware.ts:25`), and `*.frrata.shop` keeps the 308 above.
8. **Retire the old hosts** only after the overlap below. The store 308 can outlive the API alias.

**How long the old addresses keep answering (a proposal for the owner):** the store 308 for **at least 12 months** after the flip
(order emails, invoices, shared links and Google's index carry the old name, and `frrata.shop` is renewed anyway), reviewed at the 3-year renewal; the API alias
**at least 12 months and until the host's request logs show none from a released site for 30 days**, with the
retirement dated in the docs 90 days ahead. The API alias answers, it does not redirect: a browser site's CORS request would fail across a redirect.

## What existing things do during it
- **Stores:** a store has no stored address (it is derived from the name, `tenantForHost` finds it by slug), so no row changes. Old names
  (ADR-0019, `app_shop_for_name`) still redirect to the current name, on the new host.
- **Keys:** a storefront key names the shop and is hashed, never host-bound; CORS and `app_site_origin_check` compare a site's own origin, not the store domain.
  A site whose Website is its `frrata.shop` address is a store with no own domain (a test key allows localhost): re-check at
  the flip against the `sites` table. Released API versions answer the same on both hosts.
- **Cached pages:** the cache is keyed by host and tagged `shop:<t>`; the new hosts start cold for **every store at once**. Flip off-peak; speed-reviewer
  measures the origin load of a full cold start and a plan for warming the home and best-selling product pages if it is over budget.
- **Shopper cookies and carts:** `__Host-` cookies are host-only, so a shopper's bag and any cookie start afresh on the new host (the 308 does not carry them;
  `docs/research/2026-11-08-shop-addresses.md:22`). A shopper mid-bag at the flip loses it: another reason to flip off-peak and never in a sale.
- **Sign-ins:** the console, Admin and the partner workspace sign in on the console host, which does not move: staff, merchants and passkeys are untouched.
  EkCode signs in on `ekcode.in`; its ids are pairwise per shop (ADR-0009), not per host, so they hold (tenancy-auditor confirms).
- **Emails and notices:** links built from the console host and the store host are new from the flip; mail already sent keeps old links that the 308 serves.

## The secure host under a wildcard (`secure.<store>.frrata.store`)
A wildcard certificate `*.frrata.store` covers **one label**, so `<store>.frrata.store` is covered and `secure.<store>.frrata.store` is **not**
(`frata-integrations` platform.md; one-address spec § 6). So, exactly as for `frrata.shop` today:
- every `secure.<store>.frrata.store` is added to the project as its own host with its own HTTP-01 certificate, paced (explicit certificate
  creation is limited to about 30 an hour; the one-address spec § 6 paces it against Let's Encrypt's counts), and its DNS record is the same as
  its store host's: the wildcard CNAME to the project (a mismatch can cap WebKit cookies at 7 days);
- it **cannot be flattened** to `secure-<store>.frrata.store` (one label, covered): once `frrata.store` is on the Public Suffix List, each
  `<store>.frrata.store` is its own registrable domain, and `secure-<store>` would be a different site from the store, which breaks the same-site
  frame the checkout depends on. `secure.<store>` is the only shape that stays same-site after the listing;
- only one-address stores need it; a theme shop with no code site needs none. Before the flip, count the stores that already have a `secure.<store>.frrata.shop`
  (the `sites` and domains tables; the repo does not say how many, and the plan assumes none until P5·7 ships);
  each needs its new host proved and certified **before** its address switches, so the flip waits on them or they are moved one by one at step 3.

## Risks
| Risk | Severity | Handling |
|---|---|---|
| Every store cold at once; origin load at the flip | high | off-peak, outside any sale; speed-reviewer measures; warm the heaviest pages |
| A store with its `secure.` host on the old domain loses its frame | high | moved one by one, each proved first; count before the flip |
| A server-side `Host` or origin check still names the old domain | high | tenancy-auditor and security-reviewer read every comparison (items 7–11); the e2e legacy flow |
| An open redirect from the 308 | high | the redirect target is built from the matched store and the same path only; `//` and `%` paths to a 404 (P5·4's rule) |
| A released site's code or the agent's allow-list names the old API host | medium | the alias; the agent has both hosts during the overlap |
| Firewall rules miss the new API host | medium | item 14 the same hour; the rules file and the dashboard compared |
| A merchant's Razorpay website field, Search Console or Merchant Center property names the old address | medium | open question 6; a note to merchants |
| `frrata.shop` expires or is dropped while hosts still point at it | medium | renew to 3 years (owner step), reminder dated before the retirement |
| `frata.store` (the stale code default) vs `frrata.store`: one letter | low | default fixed in step 1, a unit test that the default equals the documented domain |

## Rollback
Before step 3 nothing is live: remove the new domains. After step 3 the move is reversible without data loss, because no row names a host: set
`NEXT_PUBLIC_SHOP_DOMAIN` back to `frrata.shop` and `NEXT_PUBLIC_API_HOST` to `api.frrata.shop`, clear the legacy variables, redeploy (about one build).
New-host links already sent then fail; so keep `frrata.store` attached to the project for at least 30 days after any rollback, answering a 308 the other way. The
agent environment (step 4) is versioned: re-pin `STUDIO_AGENT_VERSION` to the previous one.
