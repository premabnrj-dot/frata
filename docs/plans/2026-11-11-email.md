# Email E·0–E·2 — the sender, Frrata notices, order emails to shoppers
Status: draft, for the review agents · Date: 2026-11-11 · Spec `docs/specs/2026-11-08-messaging.md` (active, v2 approved
by the owner 2026-11-11) · Mockup https://claude.ai/artifact/TwHtjtuFPzRDv4uLqLB9xQ (v2) · ADR-0006, ADR-0008, ADR-0010
· Held: campaigns, the Messages wallet, automations (owner, 2026-11-11).

## Goal (frata-planning § North star)
Problem 1 (COD/RTO): a shopper told "Order confirmed · pay ₹2,490 on delivery" and "Shipped · arrives Thu" refuses
fewer parcels. Running Frrata: billing and security notices reach owners without a support ticket. Measures: order
emails delivered ÷ sent ≥ 98%, complaints < 0.1%; RTO on COD orders with an email vs without (Analytics, later).

## What exists (code map, 2026-11-11)
No email code; no `@aws-sdk/*`. The only mail is Supabase's sign-in OTP (`src/lib/auth/send-link.ts`). No shopper
email column (`orders`, `shop_customers`); `customer_consents` already allows channel `email`, purpose
`marketing_email`. Nothing on the server reacts to an order change: transitions live in `src/lib/orders/work.ts`
(confirm, hold, cancel, editContact, undo), `outcomes.ts` (shipped, delivered, came back, lost, undoOutcome),
`payment.ts` (markPaid), `place.ts` (placeOrder). The outbox (`src/lib/outbox/`) dispatches by `SENDERS` in
`drain.ts`, 8 tries with square backoff, `drainSoon()` after commit, daily cron. Webhooks store into `webhook_events`
and process later (billing route is the model: one URL, Frrata's own secret, 256 kB cap). Billing writes
`billing_notices` (debit_notice, failed, acknowledge) through `app_billing_notice`. Latest migration 0090; tenancy
proof at 64 checks. Members' emails live in `auth.users` only.

## Decisions (KISS, with why)
1. **No AWS SDK.** SES v2 is a JSON REST API: one `POST /v2/email/outbound-emails`, signed with SigV4. We sign with
   `aws4fetch`'s `AwsV4Signer` (MIT, ~10 kB, no deps) and send with `fetchWithTimeout` (check:fetch), so the base URL
   can point at a fake in e2e. Credentials: Vercel OIDC → STS `AssumeRoleWithWebIdentity` (a plain query call),
   cached until 5 minutes before expiry; no AWS keys in Vercel. Locally and in e2e: static keys to the fake.
2. **Templates are React components rendered with `react-dom/server` `renderToStaticMarkup`** (already a dependency);
   no React Email. Tables + inline styles, ≤ 60 kB, a plain-text part from the same data, `color-scheme` meta.
3. **One outbox kind per stream**: `email.order` (shopper emails), `email.notice` (Frrata → members). An attempt row
   (`email_messages`, ADR-0008) is committed before the request, keyed by the outbox row, so a retry after a timeout
   never sends twice (a row with `sent_at` or `provider_id` means done).
4. **Delays instead of cancels.** `enqueue` gains `notBefore`. Shipped and Delivered wait 5 minutes; every email
   re-reads the order when it sends and sends nothing if the step was undone, cancelled or already superseded.
   Finish paying waits 30 minutes and sends only if still unpaid and not cancelled.
5. **Order emails are core** (no module, every plan, on by default); a shop turns single emails off. They go to every
   shopper who gave an email, alongside WhatsApp later (owner call 2).
6. **Senders are configuration**: `EMAIL_SHOP_DOMAIN` (frratamail.app) and `EMAIL_NOTICES_FROM`
   (notices@notify.<Frrata's domain>, set this evening). Unset → that stream stays in the console only, never fails.
7. **SES tenant per shop** named `t-<tenant uuid>`, created on a shop's first send (idempotent). Events come back via
   SNS HTTPS → `/api/webhooks/ses`, signature-verified (SNS SignatureVersion 2), stored, processed later.

## Data (migration 0091 `email`, generated + custom RLS; tenancy proof 65)
- `orders.email` text null, check lower + shape + ≤ 254; erasure nulls it (`src/lib/orders/erase.ts`).
- `email_messages` (tenant): id uuid (= outbox row id), tenant_id, stream (`order`|`notice`), kind, order_id null,
  notice_id null, user_id null, provider_id null, created_at, sent_at, delivered_at, bounced_at, bounce_kind,
  complained_at, failed_at, failed_code. **No address, no body** (spec § SSOT; the address is on the order or in
  auth). State is derived from the timestamps (`src/domains/email/state.ts`). Indexes: (tenant_id, order_id),
  (tenant_id, created_at), unique provider_id.
- `email_suppressions` (tenant): tenant_id, address_hash (keyed sha256 of the lowercased address), reason
  (`bounce`|`complaint`), message_id, at, lifted_at. Per shop, never global (spec § 6).
- `shop_emails` (tenant): tenant_id, kind, off_at null, subject/preview/heading/message/button null (overrides only;
  null = Frrata's words), updated_by, updated_at.
- `notices` (tenant): id, tenant_id, type, title, body, href null, required bool, by (staff uuid null = the system),
  created_at; fan-out per shop at write (Admin "send to 214 shops" = 214 rows in one definer call).
- `notice_reads` (tenant): tenant_id, notice_id, user_id, read_at — unique (notice_id, user_id).
- `notice_prefs` (tenant): tenant_id, user_id, type, email bool — absent = the type's default.
- Grants: frata_app select/insert/update on the tenant tables (no delete), policies `tenant_id = app_current_tenant()`.
  Admin reads through definers only. Definers: `app_email_event(...)` (SES event → message + suppression, scoped by
  our message id and checked against its tenant), `app_admin_notice_fanout(...)`, `app_admin_email_health(...)`,
  `app_member_emails(tenant, roles)` (the recipient list for a notice; frata_app only, owner/admin/staff of THAT
  tenant).

## Tasks (each ends with its tests, `npm test`, typecheck, impact-reviewer on its diff)

### E·0 Foundation
0. **Regression net first:** run e2e 10-checkout, 49/50 (order work and outcomes), 52-addresses, 67-ekcode green.
1. Pure `src/domains/email/`: `kinds.ts` (order kinds, defaults wording, which event sends what, delays),
   `placeholders.ts` (menu, render, escape, links only to the shop, a missing value drops the line), `state.ts`,
   `typo.ts` (gmial → gmail etc.), `still.ts` (is this email still true for the order now). Unit tests.
2. `src/lib/email/`: `ses.ts` (SigV4 via aws4fetch + fetchWithTimeout; OIDC creds; `SES_API_BASE` locked to AWS in
   production like `MUX_API_BASE`; tenant create; send with configuration set, tags m=<message id>, t=<tenant>),
   `layouts.tsx` (shop and Frrata layouts), `render.ts`. Env names in `src/lib/env.ts` + `.env.example`.
3. Migration 0091 + definers + tenancy proof 65; `verify:tenancy`.
4. `/api/webhooks/ses`: SNS SubscriptionConfirmation (confirm only for our topic ARN), Notification → verify →
   `webhook_events` (provider `ses`, key `ses:<eventType>:<messageId>`) → `after(processSes)`; cron sweep too. Size
   cap shared via one `readCapped` in `src/lib/http/`. check:actions entry.
5. e2e fake SES (`e2e/fakes/ses.mjs`, port 4050): accepts SigV4 calls, records them (`/_test/sent`), and posts signed
   SNS notifications back for delivered/bounce/complaint (`/_test/event`), signing with a test certificate the app
   trusts only when `E2E_FIXTURES`.
6. Owner steps (docs/setup.md § Email): AWS account, SES identities frratamail.app + notify domain, OIDC role, SNS
   topic, production access request, Supabase SMTP (sign-in leaves the hourly cap). Records on Vercel DNS added by
   the agent once the owner pastes SES's values.

### E·1 Notices (screens 8–9)

   (`startSupport`; required, security), handover accepted / owner changed (required), Admin compose. Each enqueues
   `email.notice` per recipient after commit.
8. Console: the bell (a streamed slot in the sidebar head and phone header, count of unread), `/console/notices`
   (list, read on open), Settings › Your notifications (per type email switch; required types locked).
9. Admin › Notices (compose: to all shops / a plan / one shop; console only or also email; required only for
   billing/security/Frrata-action; preview; "Send to N shops"; audited).

### E·2 Order emails (screens 2–6)
10. Checkout: optional Email field under the phone; the typo hint in a lazy chunk (checkout budget 121 kB, now 120.8);
    `Address` gains `email`; `/api/shop/orders` and `placeOrder` store it; Edit contact edits it.
11. Enqueue points (inside each transition's transaction): placed COD → confirmed; prepaid placed → finish paying
    (+30 min); paid → confirmed (or payment received after a switch); shipped (+5 min); delivered (+5 min, invoice
    link); cancelled. `drainSoon()` after each console action and after placing.
12. `email.order` sender: still true? suppressed? shop email on? support email set (else hold, shown in Settings)?
    render with `brandFor`, legal footer from Settings, "Email me new drops" link (signed token) → send.
13. Settings › Emails to shoppers (sender card, 7-day strip, list with switches) and the email page (fields, Insert
    menu, live preview of a recent order in an iframe `srcdoc`, Send test to me — the signed-in member only, rate
    limited; Revert; one save bar). Support visits read only.
14. Order page: Emails card (each email's state in words; Fix the address → Edit contact; Send again; Email the
    invoice once issued). Shopper's order page: the email the updates go to; "Email me new drops" tap → a
    `customer_consents` row (shop_customers upserted by the order's phone).
15. Admin › Email health (definer counts per shop, last 7 days; SES quota; queue age alarm line).
16. e2e `69-email`: COD order with an email → confirmed email recorded by the fake; ship → after the delay (test
    clock: the row's `next_attempt_at` moved) shipped email; a bounce event → Bounced on the order, suppressed, the
    next email held; Settings switch off → not sent; edit wording → the next email carries it; notice from Admin →
    bell count → read.
