## Goal (frata-planning § North star)
Problem 1 (COD/RTO): a shopper told "Order confirmed · pay ₹2,490 on delivery" and "Shipped · arrives Thu" refuses
fewer parcels. Running Frrata: billing and security notices reach owners without a support ticket. Measures: order
emails delivered ÷ sent ≥ 98%, complaints < 0.1%; RTO on COD orders with an email vs without (Analytics, later).

## What exists (code map, 2026-11-11)
No email code; no `@aws-sdk/*`. Mail today: Supabase's sign-in OTP only (`src/lib/auth/send-link.ts`), 2 an hour. No
shopper email column (`orders`, `shop_customers`); `customer_consents` already allows channel `email`, purpose
`marketing_email`. Nothing on the server reacts to an order change: transitions live in `src/lib/orders/work.ts`
(confirm, hold, cancel, editContact — refused once packed — undo), `outcomes.ts` (markShipped, outcome() for
delivered/came back/lost, undoOutcome), `payment.ts` (markPaid, switchToCod), `place.ts` (placeOrder). The outbox
dispatches by `SENDERS` (`src/lib/outbox/drain.ts`), 8 tries with square backoff, `drainSoon()` for 20 s after commit,
and a **daily** cron — so nothing drains a delayed row on time today. Webhooks: verified, stored trimmed in
`webhook_events` (tenant-scoped since 0043), processed later; the Mux route + `app_store_mux_event` (0081) is the model.
Billing writes `billing_notices` through `app_billing_notice` (0057). Members' emails live in `auth.users` only.
Latest migration 0090; tenancy proof at 64 checks. Checkout ships 120.8 of 121 kB.

## Decisions
1. **No AWS SDK** (ADR-0011): SES v2 is JSON REST; requests signed with SigV4 by `aws4fetch`'s `AwsV4Signer` (pinned,
   `npm audit` on add) and sent with `fetchWithTimeout` (check:fetch). Endpoints are hard-coded in production
   (`email.ap-south-1.amazonaws.com`, `sts.ap-south-1.amazonaws.com`); `SES_API_BASE` is honoured only when
   `VERCEL_ENV === ''` and the host is 127.0.0.1 (the `VERCEL_API_BASE` pattern), never on a preview.
2. **Credentials: Vercel OIDC → STS `AssumeRoleWithWebIdentity`** (a plain query call). The role trusts only
   `sub = owner:premabnrj-dots-projects:project:frata:environment:production` and `aud`; policy: `ses:SendEmail` on
   the two identities + the configuration sets, `ses:CreateTenant` and `ses:CreateTenantResourceAssociation` only.
   Credentials cached in memory until 5 minutes before expiry; never logged or stored. The OIDC token is
   request-scoped: every sender runs inside a function invocation (route, action, cron, `after()`); E·0's spike proves
   `getVercelOidcToken()` works in each. Static keys only off Vercel (refused when `VERCEL_ENV` is set).
3. **Sign-in email through Supabase's Send Email Hook** (owner, 2026-11-11): `/api/auth/send-email` verifies the
   Standard Webhooks signature and sends through SES in Frrata's layout. No long-lived AWS key anywhere.
4. **Templates are plain TypeScript with an escaping `html` tag** (`src/domains/email/html.ts`, layouts in
   `src/domains/email/layouts.ts`): pure, unit-tested, no framework (Next restricts `react-dom/server`; built
   2026-11-11 instead of the spike). Every value is escaped unless already built by the tag; links https only; colours
   6-digit hex only. Tables + inline styles, ≤ 60 kB, a text part from the same data, `color-scheme` meta. Content is
   always `Simple`, never Raw.
5. **Channel-neutral rules in `src/domains/messaging/`** (ADR-0010 one engine): `events.ts` (which order event sends
   what, delays), `still.ts` (is this message still true: `orderState(o, now)` + "this event was not undone"),
   `placeholders.ts`. Email-only rules in `src/domains/email/`: words and defaults, `typo.ts`, `state.ts`, `shape.ts`
   (the one email rule, with a parity test against the SQL CHECK). WhatsApp at M·1 reuses `messaging/`.
6. **Enqueue inside the writers, keyed by the event**: `placeOrder`, `markPaid`, `switchToCod`, `markShipped`,
   `outcome()` (delivered), `cancel` each enqueue in their own transaction with dedupe key `email:<kind>:<eventId>` and
   payload `{orderId, eventId}` (ids only — a test asserts the keys), only when `orders.email` is set. Shiprocket later
   gets the emails for free. Undo-and-redo makes a new event, so a new email. `enqueue` gains `notBefore`.
7. **Delays, then re-check**: Shipped and Delivered wait 5 minutes; Finish paying waits `HOLD_MINUTES` and sends only
   when `orderState === 'payment_abandoned'`. A switch to COD enqueues Confirmed (COD). Every send re-reads the order.
8. **A drain every 5 minutes** (Vercel Pro, owner 2026-11-11): new `/api/cron/drain` (`*/5 * * * *`, its own
   `maxDuration`) drains the outbox and sweeps SES events only; the daily job stays as it is. Before any sender ships,
   the outbox claim moves into a definer (setup.md § Later item 2; tenancy: the null-tenant branch of 0017).
9. **Attempt rows, honestly** (ADR-0006/0008): the `email_messages` row (id = our message id) is inserted with
   `attempted_at` before the SES call; the id travels as tag `m`. SES has no idempotency key: a retry of an attempted
   row with no `provider_id` waits 15 minutes for an event carrying `m`, and only then resends. A duplicate is still
   possible when SES accepted, we timed out and no event ever arrives — written down, rare.
10. **Skips are outcomes, never holds**: suppressed, off, not true any more, no support email, shop closed, daily cap →
    `skipped_at` + `skip_code`, the row is done, the Emails card says why. No row burns 8 tries waiting.
11. **Throttling**: SES 429 and 5xx → `deferRow` (no attempt spent); concurrent drains capped by an advisory lock;
    one multi-row `enqueue` for bulk transitions. Production access asks for ≥ 1M a day and 50/s.
12. **SES tenant per shop, set up ahead**: a paced `email.tenant` outbox kind (control-plane calls are 1/s) runs when
    a shop's first email is enqueued; `email_shops.ses_ready_at` records it; a send before it is ready defers.
    Notices use Frrata's own tenant `frrata` and configuration set `notices`.
13. **One suppression list, ours**: the configuration sets turn SES's account-level suppression off
    (`SuppressedReasons: []`), so a bounce at shop A never blocks shop B. Our `email_suppressions` is keyed per shop:
    HMAC(key id, tenant ‖ lowercased address) from `src/lib/crypto/key-ring.ts`, never the same value across shops.
14. **Events**: the configuration set publishes Delivery, Bounce, Complaint, Reject only (no Send/Open/Click/Delay),
    to an SNS topic with `SignatureVersion=2`, raw delivery off, "include original headers" off. The route checks,
    in order and before any fetch: header and body `Type` agree; `TopicArn` equals the env ARN (every type);
    `SignatureVersion === '2'`; `SigningCertURL` https, host exactly `sns.ap-south-1.amazonaws.com`, path
    `/SimpleNotificationService-*.pem`, fetched with a timeout and cached per instance; `SubscribeURL` same host,
    `Action=ConfirmSubscription`, its TopicArn equal, `redirect: 'manual'`; `Timestamp` within an hour. Then
    `app_store_ses_event` routes **only by tag `m` → `email_messages.tenant_id`** (tag `t` is a cross-check; unknown
    `m` or mismatch → stored nowhere) and stores a trimmed payload: eventType, m, bounce type/subtype, timestamp —
    never destination, headers or diagnosticCode. Failures after a good signature answer 5xx (SNS retries only
    5xx/429). The e2e certificate is trusted only when `VERCEL_ENV === '' && E2E_FIXTURES` with a 127.0.0.1 URL.
15. **Abuse limits, failing closed**: per keyed email hash per shop (3 orders' worth an hour) and globally; a daily
    cap for a shop that is new or not yet open; first name only, ≤ 30 characters, in subjects; From display name
    stripped of `"<>,;` and controls then RFC 2047-encoded; subjects stripped of C0 and capped at 150; Reply-To only a
    validated support email; emails show the phone and address masked like the order page.
16. **Errors as codes**: SES error text can name the address; the sender throws codes only (`ses_429`,
    `ses_rejected`…), `failed_code` is an enum, `outbox.last_error` never carries a provider's words.

## Data (migration 0091 `email`, generated + custom; tenancy proof 65)
- `orders.email` text null (CHECK = `shape.ts`, lower, ≤ 254, local part ≤ 64); editable until the order is erased
  (its own Edit contact field, not refused after packing); erasure nulls it.
- `email_messages` (tenant): id, tenant_id, kind, order_id null, event_id null, notice_id null, user_id null,
  provider_id null, created_at, attempted_at, sent_at, delivered_at, bounced_at, bounce_kind, complained_at,
  failed_at, failed_code, skipped_at, skip_code. **No address, no body.** State derived (`state.ts`); stream derived
  from kind. Indexes: (tenant_id, order_id) where order_id is not null; (tenant_id, created_at); unique
  (notice_id, user_id) where notice_id is not null. No provider_id index (events find rows by id). Deleted after 180
  days and with the order on erasure.
- `email_suppressions` (tenant): tenant_id, address_hash, key_id, reason (`bounce`|`complaint`), message_id, at,
  lifted_at; unique (tenant_id, address_hash) where lifted_at is null.
- `shop_emails` (tenant): tenant_id, kind, off_at, subject/preview/heading/message/button null (overrides; plain text),
  updated_by, updated_at; unique (tenant_id, kind).
- `email_shops` (tenant): tenant_id pk, ses_ready_at, daily_cap. 
- `email_daily` (tenant): day, tenant_id, sent, delivered, bounced, complained, skipped — the cron's roll-up, read by
  Settings and Admin health.
- `notices` (tenant): id, tenant_id, type, source_kind, source_id (e.g. the billing notice), title null, body null
  (Admin's words; plain text), href null (a `/console/` path), required, batch_id null, by null, created_at; index
  (tenant_id, created_at desc). **frata_app may read, never insert** — definers only, so a shop can't forge a
  "Frrata, required" notice. Worded when rendered, from its source.
- `notice_reads` (tenant): tenant_id, notice_id, user_id, read_at; unique (notice_id, user_id). The server binds
  user_id to the session user; nothing is written during a support visit.
- `notice_prefs` (tenant): tenant_id, user_id, type, email; required types refused on the server.
- Policies `using` + `with check` `tenant_id = app_current_tenant()`; revokes from anon, authenticated, service_role;
  no delete grants. Definers (`search_path ''`, one role each, revoked from service_role):
  `app_store_ses_event`, `app_apply_ses_events`, `app_member_email(user_id)` (bound to `app_current_tenant()`,
  returns one address for a current member, billing types owner/admin only), `app_admin_notice_fanout(staff, audience,
  …)` (computes tenants from the audience, inserts notices + one outbox row each, ids only, in one transaction, with
  `batch_id`; audited), `app_admin_email_health(staff, days)` (counts from `email_daily` + queue age; frata_admin
  only), `app_outbox_claim` (the claim without the null-tenant branch). `app_billing_notice` and the support-visit
  start also insert their notice + outbox row in the same transaction. Outbox: sent/dead rows deleted after 30 days,
  processed `ses` events after 30 days (definer, cron).
