## Goal
Ranked problems (5) a premium store built as code and (7) festive-peak reliability. Content stops living inside the
look, so a theme store's banner, menu, FAQ or Contact line is saved live from the console today, and a code site (V2)
reads the same rows through the Storefront API later with nothing moved again. Measures (spec § Goal) count from the
first handed-over code site; this phase is the gate "Console › Content live before the first handover".

## Design (from the spec; decisions in § Decisions)

### `site_content` (one migration, generated + a `--custom` access migration)
`id`, `tenant_id` (FK tenants, cascade), `kind` text CHECK in `CONTENT_KINDS` = `('announcement','menu','contact')`
(placement joins in V2), `key` CHECK `^[a-z0-9.-]{1,40}$`, `value jsonb` CHECK `octet_length(value::text) <= 32768`,
`previous jsonb` (same cap), `starts_at`, `ends_at` (CHECK `ends_at > starts_at`), `stopped_at`, `version int default 1`,
`updated_at`, `updated_by uuid`, `created_at`. `unique (tenant_id, id)`, `unique (tenant_id, kind, key)` (also the read
index), CHECK menus' keys in `('main','footer','tabs')` and contact's key `'contact'`, CHECK dates only on
`announcement`. Access (`--custom`): `grant select, insert, delete` + `grant update (value, previous, starts_at,
ends_at, stopped_at, version, updated_at, updated_by)` to `frata_app`; revoke all from `anon, authenticated,
service_role`; no `frata_admin` grant; RLS on, `tenant_rows` policy `using` + `with check`; cap trigger
`app_site_content_cap` (≤ 3 announcements, one row per menu key, one contact) that checks `new.tenant_id =
app_current_tenant()` **before** taking the `content:<tenant>` advisory lock (as `app_shop_pages_cap`). Notices:
`notices_source` CHECK gains `'content'` (used by the move's notice now, the partner line later).
**tenancy.sql block 80** (renumbered at merge): no tenant set reads 0 and an insert with none raises; A sees only A; insert with B's tenant raises;
update/delete of B's row changes 0; updating `tenant_id`, `kind`, `key` raises (column grant); anon, authenticated,
service_role, frata_admin hold nothing; the cap trigger refuses B before the lock (and gets **no** `is null` branch); a fourth live announcement raises;
`app_site_content_cap` and `app_move_content` are not `prosecdef`, have `search_path` set, and no role (public, anon,
authenticated, service_role, frata_app, frata_admin) holds EXECUTE; `has_table_privilege` false for frata_admin and the
API roles; the two-tenant move check (B's rows and notices hold nothing of A's). **Block 70** (`shop_pages`) is rewritten:
pointing a page at B's publish now raises `insufficient_privilege` (the column grant is revoked).
`notices_source` is redefined with every existing value kept (`addon_trial`, `edit_payment` …) plus `content`.

### Pure rules: `src/domains/content/`
- `kinds.ts`: `CONTENT_KINDS`, `MENU_KEYS`, value schemas: announcement `{ text: plainText(120), link: shopPath | null,
  scheme: 'paper'|'tint'|'ink' }`; menus reuse `MenusSchema`/`MENU_LIMITS` from `themes/site.ts` (moved here, `site.ts`
  re-exports for released manifests), with `plainText` on labels; contact `{ line: plainText(160) }`.
- `plain-text.ts`: `plainText(max, { lines })` (spec § plain-text rule: NFC; refuses `\p{Cc}` but `\n` in long text,
  `\p{Cf}` except ZWNJ/ZWJ, `\p{Co}`, `\p{Cn}`, `< > { } \`); a unit test per refused class, Hindi and Tamil kept.
- `schedule.ts`: `entryState(row, now)` → `scheduled | live | ended | stopped` from the columns (no status stored);
  the bar's chips read it.
- `bar.ts`: **the one order rule** `barFor(offer, written, now)`: a live offer first (owner decision 7); else the live
  written entry that started last (ties: last saved). Read by the shop's frame and by the console's chips ("Live now",
  "Behind the offer", "Behind <text>").
- `who.ts`: `contentSaver(role, hasOwner, supportSessionId)` → `'yes' | 'support' | 'after_handover' | 'read_only'`:
  owner, admin yes; partner yes only while `!hasOwner`; staff read only; a support visit refused. ADR-0015's
  `content.write` maps onto this function when lane C lands `CAPABILITIES` (no tuple added to `roles.ts` here).

### The read seam: `src/lib/queries/content.ts`
- `shopContent(tenantId)`: `shopCached('content-v1', 'content', …)` (it wraps `cache` itself; a unit test asserts the
  tags `shop:<t>` and `shop:<t>:content`), one statement `select kind, key, value,
  starts_at, ends_at, stopped_at from site_content where tenant_id = $1`; **every row is parsed at read** with its
  kind's tolerant reader (part by part, as `readMenus` does today; a row that fails reads as no row, links checked
  against `SHOP_PATH`), so nothing unparsed reaches a shell (security M3). **Revalidate 60 s** (speed H1, security M5:
  the purge limiter may drop a purge and trusts the 60 s backstop; one indexed statement a shop a minute). Tags
  `shop:<t>` and `shop:<t>:content`: `'content'` joins the scope union **and** the tag branch in `storefront.ts:50-52`
  and `refreshShop`'s union (`refresh.ts:9`). Schedule applied at render with the request's `now` (`barFor`).
  Pages and FAQ keep the existing `pages` scope (spec's `content-pages`: same job, existing tag; recorded choice).
- `previewContent(tenantId)`: the same core, uncached, for the two preview routes (inside their existing `Promise.all`)
  so the merchant never sees a row older than their save (speed 8).
- `contentForConsole(tx, tenantId, tab)` (uncached, the editor, reads only the open tab): rows with `version`,
  `updated_at`, and `updated_by` resolved **on the server to that one member's first name** through the tenant-bound `app_shop_people()`
  (0072:68), never a lookup by user id; a past member reads "a former member" (never an email: security
  M2; `app_shop_people` is not called on this page); for Menus, only `settings->'header'` and `settings->'bottomTabs'`
  of the live revision through `liveRevision(tx, …)` (`look.ts:87`), never `shopLook`/`shopTheme` in the transaction
  (speed 7, P4); Pages and FAQ also read `shop_pages` and the bound answers' settings in the same `Promise.all`.
- `shopPages`/`previewPages` stay in `queries/pages.ts` (spec: `shop_pages` kept); the API will read both.

### The shop
`ShopFrame` reads `shopTheme(shop)`, `shopContent(shop.id)` and `shopAnnouncement(shop.id)` with one `Promise.all`,
each read outside any transaction, content and offer each `.catch(() => null)` (a failure: menus from the collections,
no bar, never an error page; speed 5). `ShopShell` takes `content` as a **required** prop and `ResolvedTheme`,
`ThemeLayer` and `ThemeSettings` (`types.ts:53`) lose `menus`, `contact` and `announcement`, so `tsc` finds every caller
(architecture 4): the gated OpeningSoon shells (`_frame.tsx:18,20`), `(order)/layout.tsx:12-13`, `preview-body.tsx:67`,
the customizer (`customize/page.tsx:97`, `editor.tsx:209,248,254`), the theme preview, `/console/preview`, Settings'
previews, `/policies/contact`, the share card, `thumb.tsx:15`. Menus with no row still fall back to the collections
(`menusOf`); a stored `[]` is an empty menu. Pages: `/pages/*` and the sitemap unchanged. A cold shop page reads one
more cached entry (≤ 12 statements held; counted in task 4), up to 5 connections at once on a cold render (pool 10).

### Console › Content (`src/app/(console)/console/content/`)
- Route `/console/content` with `?tab=announcement|menus|pages|faq|contact` (`ViewTabs`), nav item **Content** in the
  Store group after Offers (shared file: the console layout), More on a phone. `requireMember(ANY_MEMBER)` on the page;
  staff and partners after handover see it read-only (Edit `aria-disabled`, one chip "<Owner> saves this").
- **Announcement:** ≤ 3 entries, each a row: text, chip from `entryState` + `barFor`, dates, link; Add / Edit in a
  `Dialog` (sheet on a phone): Text (counter /120), Link (picker of the store's pages: `targets` as Look has them),
  Colour (`Segmented` Paper · Tint · Ink), Starts, Ends (optional; a mistake at the field: "Ends after it starts");
  More: End now (sets `stopped_at`), Delete (8 s Undo). A live offer shows as the first row, read-only, "Offers ›".
- **Menus:** Main (3 levels), Footer (1), Phone tabs (≤ 5, icon each, shown when the look has bottom tabs) as Look v4
  draws them: rows with Up, Down, Under the one above, Out a level; Add a link (picker); counts "6 of 12"; one Save per
  menu (an explicit save: shoppers see it) with the Unsaved changes bar, then the 8 s Undo toast.
- **Pages:** the store's pages but the FAQ (About and later ones), each a row: title, address (mono), chip Shown or
  Hidden; Add a page (About only while none; ≤ 20); Edit opens the page's words and photos (the template's fields, the
  same `PageForm` fields Look used, moved into `src/components/content/`), the address (fixed once live), Hide. Save is
  live, Undo 8 s. Example words still refuse a save ("Write your own words for <field>").
- **FAQ:** questions with ↑ ↓, Edit, Remove (Undo); ≤ 12; a bound answer shows its words read-only with the chip "From
  your settings" and "Change in Settings"; Save per question; Add a question; the FAQ page is made on its first
  question.
- **Contact line:** one field (counter /160), the business details from Settings read-only below it ("From your
  Settings" box, Change in Settings), Save.
- **Feedback:** toast "Menu saved" + Undo (8 s; `previous` swapped back under the version the save returned); a stale
  version is an error toast "Riya changed this at 10:42 pm" + Reload; a refusal says what is safe ("We couldn't save
  that. Nothing was changed."); a support visit sees the banner and every Edit disabled.

### Actions (`src/app/(console)/console/content/actions.ts`)
`saveAnnouncement`, `endAnnouncement`, `deleteAnnouncement`, `saveMenu`, `saveContact`, `savePage`, `addPage`,
`hidePage`, `saveQuestion`, `moveQuestion`, `removeQuestion`, `undoContent`. Each:
- `asMember(CAN_BUILD, …)`; a support visit refused by its session before any write (as the Look).
- Inside the transaction: `hasOwnerIn(tx, tenantId)`, **moved out of `costsVisibleIn`** (`queries/settings.ts:82-87`, which then calls it): a
  count of 0 means no tenant context and reads as "has an owner"; errors propagate (security M1). `contentSaver` is an
  allow-list: owner, admin yes; partner only while `!hasOwner`; every other role, and any future one, `read_only`.
  (Staff never reach it under `CAN_BUILD`: its staff branch serves the read-only page only; architecture 11.)
- The limiter `LIMITS.contentSave` (30 a minute a shop, `failClosed = true`, counted after `contentSaver` so a refused
  partner never spends the owner's saves; Undo has its own bucket `contentUndo`: security L1).
- Zod with the domain schemas (strict `plainText` on save only), a byte check per menu ("This menu is too long",
  before the 32 kB CHECK; a menu is capped at 60 items in all: speed 3, security L2); links match `SHOP_PATH`
  (`sections.ts:25`); page images through `cleanFill` / `acceptedBase(…, 'theme')`.
- A conditional update `where tenant_id = … and id = … and version = $seen` (0 rows → stale: "Riya changed this menu
  today, 10:42 pm. Reload to see it.", the first name only); `previous := { value, starts_at, ends_at, stopped_at }`
  (the whole entry, so Undo restores dates too), `version + 1`, `updated_by := auth user`. Delete is a soft
  `deleted_at` (a column; reads skip it), so Undo has a row and the cap counts only live rows.
- **Undo is bounded** (security H2): `undoContent(id, version)` needs `version = the save's`, `updated_by = caller`,
  `now() - updated_at ≤ 60 s`, a non-null `previous`; it runs `contentSaver`, the kind's schema and `cleanFill` on
  `previous` again, and clears `previous` after use. No other path restores an older value.
- The tenant for every write, audit row, `acceptedBase` and purge is `asMember`'s, never a row's or the form's;
  `undoContent`, `endAnnouncement` and `deleteAnnouncement` use the same `tenant_id + id + version` clause.
- Audit: one row through `memberAudit` (`src/lib/auth/member-audit.ts`; skips support visits, which `asMember` audits
  already): action `content.save|end|delete|undo`, target the row id, detail the kind, key, version and field names
  only, never the words.
- Errors: `23514`/`22P05` and the rest caught, logged as `errName` only (S10); the reply in words, nothing changed.
- After the commit, the purge: one `throttledPurge(tenant, scope, { purge, trail })` replaces `refreshSoldOut`'s body
  (`refresh.ts:39-71`; `refreshSoldOut` calls it with `soldOutPurge`/`soldOutTrail`, content with
  `contentPurge`/`contentTrail`): the **first save in a window purges at once**, repeats queue one trailing purge
  across instances; where no trailer fits it purges now; the 60 s backstop covers the rest (architecture 7, speed 1
  and 4). Page and FAQ saves purge `shop:<t>:pages` only.

### The move (one release)
**A deviation from the spec, with its reason** (architecture 5): the spec says "a per-tenant script inside
`withTenant`"; production is reached only through the Supabase API (CLAUDE.md § Deploying), so the copy is a SQL
function run as `postgres`, which bypasses row policy. It therefore sets `set_config('app.tenant_id', t, true)` per
tenant in a loop over `tenants` (the cap trigger and any policy see the right shop: speed 2a, tenancy H1), names
`tenant_id = t` in every statement and `(tenant_id, …)` in every join, and clears the setting after the loop.
- **Migration `NNNN_site_content_move.sql`** (renumbered at merge; applied by the orchestrator before the push):
  `app_move_content()` (security invoker, revoked from every role). Per tenant: the **live** revision exactly as
  `liveOf` derives it (`distinct on (theme_key, theme_version)` ordered `published_at desc, id desc`, newest first,
  minus **withdrawn** versions only, not recalled: `look.ts:38-45`, `release.ts:43`; joins on `(tenant_id,
  revision_id)`), then its layer's `settings.announcement` (one entry, no dates, its scheme kept), each of
  `menus.main|footer|tabs` that is set (`null` or absent: no row, so the collections fallback stays; `[]`: an empty-menu
  row), and `contact` only where `trim(line) <> ''` (as `readContact`). **Values are copied verbatim** (no SQL twin of a
  text rule: the tolerant read decides at render, the strict rule applies at the next save; architecture 3, security
  M3); a value over 32 kB is skipped and named in the notice (speed 2b).
- **Reconciling re-run** (architecture 1, security M4): `on conflict (tenant_id, kind, key) do update … where
  site_content.updated_by is null` (no person has saved it), and moved rows no person touched whose part is now absent
  are deleted; a tenant whose content a person saved is never touched. Run at the end of the migration, then by the
  orchestrator once the new production deployment is Ready (old tabs then reach new code), and once more 24 hours
  later; then a later migration drops the function. The notice is written only when this run inserted or
  dropped something and the tenant has no `source_kind = 'content'` notice yet (architecture 9); it names items by place
  ("Main menu, link 3"), never by their words, under 1,000 characters (tenancy M1).
- Drafts are not copied: where the shop's draft layer differs in those three parts, one Inbox notice (`type
  needs_you`, `source_kind content`, href `/console/content?tab=menus`) "Your menus, bars and Contact line are now in
  Content" / "Unpublished menu changes were not moved".
- `shop_pages`: `draft := live` for live pages (a differing draft named in the notice), `previous := null` (no stale
  Undo: security H2), a never-published page becomes Hidden. In a **separate short migration**, after the backfill
  commits, with `set local lock_timeout = '2s'`: drop the FK `shop_pages_live_publish` (it locks
  `shop_theme_publishes`: speed 2c) and revoke `live_publish_id` from `frata_app`'s column grant
  (`0100_shop_pages_access.sql:19`); tenancy.sql's check at 2774-2776 then expects `insufficient_privilege`
  (architecture 2). "Address fixed" and "never published" are re-derived from `live`/`previous` only
  (`queries/pages.ts:44`, `page-actions.ts:67,104` go with the file: below); `discardPages` and `undoPages` leave the
  look's Discard and Undo in the same task (architecture 4, 10). The backfill is timed at the 10× seed (500 shops)
  and the figure written here before release.
- **A parity int test** (`site-content-move.int.test.ts`) seeds shops (two versions, a withdrawn and a recalled one,
  Undo, a draft, a `null` and an `[]` menu, a 40 kB menu, a blank contact) and checks the SQL picks the same revision
  as `liveOf`, copies exactly its parts, and that a publish between two runs is reconciled while a person's save is
  kept; as `app_trial_recompute`'s.
- **Old writers deleted** (security H1): `look/page-actions.ts` (`addPageAction`, `savePageAction`,
  `removePageAction`) is removed; `saveLookAction` stops writing menus and contact; a test proves only
  `content/actions.ts` writes `shop_pages` and `site_content` (and the move's migration).
- The old text schemas remain only where released manifests need them (`AnnouncementSchema` in `manifest-schema.ts:77`);
  `ContactSchema` and the menus' old `PLAIN` leave with the layer (architecture 6).
- **The Look stops writing them:** `LayerSchema` drops `menus` and `contact`, `SettingsSchema` drops `announcement`
  (stored layers keep the keys; Zod strips them on read), `layerProblems`, `carryOver`, `saveLookAction`, `cleanImages`
  and `page-readiness.ts` stop touching them; `preparePages`/`undoPages`/`discardPages` leave `publishRevision`, Undo
  and Discard; Look's thumb (`thumb.tsx:15`) draws the content bar. Released manifests keep `announcement: null`
  (manifests never change); `resolveTheme` ignores it.
- **The Look's panels become links:** the customizer's Menus tab, Style › Header's bar, the Contact page and each page
  in the page picker show one row "Edit in Content ›" (a full link to the tab). The preview still draws the live
  content.
- **The proof:** `src/domains/content/__tests__/no-layer-readers.test.ts` reads every file under `src/` (comments
  skipped, CLAUDE.md "a gate must not match its own documentation") and fails on `layer.menus`, `.menus` off a layer or
  `ResolvedTheme`, `settings.announcement`, `layer.contact`, `readMenus(`, `readContact(`; it runs against the file
  that describes it.

## Decisions (taken in this plan, within the spec)
1. The bar's written entries: the one that **started last** shows when several are live (a sale's bar replaces a
   standing one without deleting it). Offer first (owner decision 7).
2. The bar keeps its colour (Paper · Tint · Ink) on the entry: it moves with the text, so no store's bar changes.
3. Menus keep today's names and limits (`main`, `footer`, `tabs`; 3 levels, 12 items, 5 tabs, labels 40).
4. A page or menu saves with one explicit Save (shoppers see it at once: frata-design-language Phase 1 "never autosave
   what shoppers see"); entries and questions save from their dialog.
5. The move's lost drafts are told once, as an Inbox notice, never by reading the old layer again.
6. Pages: save is live; a never-published page becomes Hidden; `live_publish_id` dropped later with the function.

## Design review (frata-planning § 3; the spec's review holds, these are this phase's own)
- **UI/UX:** one primary per dialog (Save); states per tab: empty (No announcement yet · Add), one, full ("3 of 3"),
  scheduled, live, behind the offer, ended, stopped, read-only (staff, partner after handover), support visit, stale,
  refused, saving, phone. Constraints over refusals: links from a picker, dates from a picker, counters. Undo 8 s.
- **Tenancy:** § `site_content`; tenant only from `requireMember` or the host; the move per tenant joins on
  `(tenant_id, revision_id)`; no `frata_admin` grant; `updated_by` never leaves the console.
- **Modularity:** domain pure; one read seam; actions in one file; components under `content/`; Look imports nothing
  from content but the link.
- **SSOT:** one row per fact; the bar's order once (`bar.ts`); state from dates; menus' schema moved, not copied.
- **YAGNI/KISS:** no drafts, no preview token, no placements, no seasons; a closed set of three kinds.
- **Performance:** (a) shop frame: theme ‖ content ‖ offer in one `Promise.all` (net −1 serial read); Content page:
  one transaction, the open tab's rows + two look settings in `Promise.all`; (b) the unique `(tenant_id, kind, key)`
  index serves the one read (≤ 7 rows a shop; no 10× EXPLAIN needed: architecture 12); (c) entry ≈ 40 kB worst case
  (main 32 kB, footer ≈ 4 kB, tabs ≈ 2 kB, bars ≈ 2 kB, contact 0.5 kB), size test; (d) no shop HTML growth beyond
  today's menus (a 32 kB main menu measured in task 3); (e) a save purges `shop:<t>:content` (every page once; first save at once, repeats ≤ once per 30 s, one trailer; 60 s backstop),
  a page save `shop:<t>:pages` only; (f) no new shop JS; Content's console JS within 150 kB (dialogs load on open);
  (g) nothing preloaded.
- **Reliability:** no outbound call; a failed save says nothing changed; the trailing purge never drops the last save.
- **Security:** `contentSaver` inside the transaction; support refused by its session; Zod + `plainText` caps; links
  shop paths only; images by `acceptedBase`; limiter fail closed; audit with field names, previous value in the row;
  merchant words render as React text, never HTML.
- **Motion:** § Feedback toasts; Dialog/sheet; Segmented; no new motion.
- **Unit economics:** none: data writes, no model, sandbox or build.
- **Blast radius:** `resolve.ts`, `layer.ts` (carryOver, schemas), `site.ts`, `shell.tsx`, `_frame.tsx`, previews,
  policies page, share card, `thumb.tsx`, the customizer (`editor.tsx`, `theme-form.tsx`, `pages-panel.tsx`,
  `page-form.tsx`, `menus-form.tsx`), `look.ts` (publish/undo/discard), `pages.ts`, `page-readiness.ts`,
  `page-actions.ts`, `refresh.ts`, `storefront.ts` (`shopCached` union), the console layout (nav), notices CHECK.
