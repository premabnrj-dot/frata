## Goal
Ranked problems (5) a premium store built as code and (7) festive-peak reliability. Content stops living inside the
look, so a theme store's banner, menu, FAQ or Contact line is saved live from the console today, and a code site (V2)
reads the same rows through the Storefront API later with nothing moved again. Measures (spec § Goal) count from the
first handed-over code site; this phase is the gate "Console › Content live before the first handover".

## Design (from the spec; decisions in § Decisions)

### `site_content` (one migration, generated + a `--custom` access migration)
`id`, `tenant_id` (FK tenants, cascade), `kind` text CHECK in `CONTENT_KINDS` = `('announcement','menu','contact')`
(placement joins in V2), `key` CHECK `^[a-z0-9.-]{1,40}$`, `value jsonb` CHECK `octet_length(value::text) <= 32768`,
`previous jsonb` (same cap), `starts_at`, `ends_at` (CHECK `ends_at > starts_at`), `stopped_at`, `version int default 1`,
`updated_at`, `updated_by uuid`, `created_at`. `unique (tenant_id, id)`, `unique (tenant_id, kind, key)` (also the read
index), CHECK menus' keys in `('main','footer','tabs')` and contact's key `'contact'`, CHECK dates only on
`announcement`. Access (`--custom`): `grant select, insert, delete` + `grant update (value, previous, starts_at,
ends_at, stopped_at, version, updated_at, updated_by)` to `frata_app`; revoke all from `anon, authenticated,
service_role`; no `frata_admin` grant; RLS on, `tenant_rows` policy `using` + `with check`; cap trigger
`app_site_content_cap` (≤ 3 announcements, one row per menu key, one contact) that checks `new.tenant_id =
app_current_tenant()` **before** taking the `content:<tenant>` advisory lock (as `app_shop_pages_cap`). Notices:
`notices_source` CHECK gains `'content'` (used by the move's notice now, the partner line later).
**tenancy.sql block 80** (renumbered at merge): no tenant set reads 0; A sees only A; insert with B's tenant raises;
update/delete of B's row changes 0; updating `tenant_id`, `kind`, `key` raises (column grant); anon, authenticated,
service_role, frata_admin hold nothing; the cap trigger refuses B before the lock; a fourth announcement raises.

### Pure rules: `src/domains/content/`
- `kinds.ts`: `CONTENT_KINDS`, `MENU_KEYS`, value schemas: announcement `{ text: plainText(120), link: shopPath | null,
  scheme: 'paper'|'tint'|'ink' }`; menus reuse `MenusSchema`/`MENU_LIMITS` from `themes/site.ts` (moved here, `site.ts`
  re-exports for released manifests), with `plainText` on labels; contact `{ line: plainText(160) }`.
- `plain-text.ts`: `plainText(max, { lines })` (spec § plain-text rule: NFC; refuses `\p{Cc}` but `\n` in long text,
  `\p{Cf}` except ZWNJ/ZWJ, `\p{Co}`, `\p{Cn}`, `< > { } \`); a unit test per refused class, Hindi and Tamil kept.
- `schedule.ts`: `entryState(row, now)` → `scheduled | live | ended | stopped` from the columns (no status stored);
  `liveEntries(rows, now)`.
- `bar.ts`: **the one order rule** `barFor(offer, written, now)`: a live offer first (owner decision 7); else the live
  written entry that started last (ties: last saved). Read by the shop's frame and by the console's chips ("Live now",
  "Behind the offer", "Behind <text>").
- `who.ts`: `contentSaver(role, hasOwner, supportSessionId)` → `'yes' | 'support' | 'after_handover' | 'read_only'`:
  owner, admin yes; partner yes only while `!hasOwner`; staff read only; a support visit refused. ADR-0015's
  `content.write` maps onto this function when lane C lands `CAPABILITIES` (no tuple added to `roles.ts` here).

### The read seam: `src/lib/queries/content.ts`
- `shopContent(tenantId)`: `cache(shopCached('content-v1', 'content', …))`, one statement `select kind, key, value,
  starts_at, ends_at, stopped_at from site_content where tenant_id = $1`, raw rows (≤ 7, ≤ 3 × 32 kB worst case),
  revalidate 86,400 s, tags `shop:<t>` and `shop:<t>:content` (new scope in `shopCached`'s union and `refreshShop`).
  Schedule applied at render with the request's `now` (`liveEntries`), never inside the cache.
- `contentForConsole(tenantId)` (uncached, the editor): rows with `version`, `updated_at`, `updated_by`'s email through
  the members definer the console already uses; the live look's `header` and `bottomTabs` (menus' row limit and tabs
  hint) through `look.ts` (no second `withTenant`: one transaction, `Promise.all`).
- `shopPages`/`previewPages` stay in `queries/pages.ts` (spec: `shop_pages` kept); the API will read both.

### The shop
`ShopFrame` reads `shopTheme(shop)`, `shopContent(shop.id)` and `shopAnnouncement(shop.id)` with one `Promise.all`
(today the offer read waits for the theme: this removes a serial round trip). `ShopShell` takes `content` (live menus,
the bar from `barFor`, contact) as a prop; `ResolvedTheme` loses `menus`, `contact` and `settings.announcement`
(`resolve.ts` stops `readMenus`/`readContact`); menus with no row still fall back to the collections (`menusOf`).
The theme preview (`(lookpreview)`), `/console/preview`, Settings' previews, the policy pages (`/policies/contact`)
and the share card read `shopContent` (or the console read) the same way. Pages: `/pages/*` and the sitemap unchanged.

### Console › Content (`src/app/(console)/console/content/`)
- Route `/console/content` with `?tab=announcement|menus|pages|faq|contact` (`ViewTabs`), nav item **Content** in the
  Store group after Offers (shared file: the console layout), More on a phone. `requireMember(ANY_MEMBER)` on the page;
  staff and partners after handover see it read-only (Edit `aria-disabled`, one chip "<Owner> saves this").
- **Announcement:** ≤ 3 entries, each a row: text, chip from `entryState` + `barFor`, dates, link; Add / Edit in a
  `Dialog` (sheet on a phone): Text (counter /120), Link (picker of the store's pages: `targets` as Look has them),
  Colour (`Segmented` Paper · Tint · Ink), Starts, Ends (optional; a mistake at the field: "Ends after it starts");
  More: End now (sets `stopped_at`), Delete (8 s Undo). A live offer shows as the first row, read-only, "Offers ›".
- **Menus:** Main (3 levels), Footer (1), Phone tabs (≤ 5, icon each, shown when the look has bottom tabs) as Look v4
  draws them: rows with Up, Down, Under the one above, Out a level; Add a link (picker); counts "6 of 12"; one Save per
  menu (an explicit save: shoppers see it) with the Unsaved changes bar, then the 8 s Undo toast.
- **Pages:** the store's pages but the FAQ (About and later ones), each a row: title, address (mono), chip Shown or
  Hidden; Add a page (About only while none; ≤ 20); Edit opens the page's words and photos (the template's fields, the
  same `PageForm` fields Look used, moved into `src/components/content/`), the address (fixed once live), Hide. Save is
  live, Undo 8 s. Example words still refuse a save ("Write your own words for <field>").
- **FAQ:** questions with ↑ ↓, Edit, Remove (Undo); ≤ 12; a bound answer shows its words read-only with the chip "From
  your settings" and "Change in Settings"; Save per question; Add a question; the FAQ page is made on its first
  question.
- **Contact line:** one field (counter /160), the business details from Settings read-only below it ("From your
  Settings" box, Change in Settings), Save.
- **Feedback:** toast "Menu saved" + Undo (8 s; `previous` swapped back under the version the save returned); a stale
  version is an error toast "Riya changed this at 10:42 pm" + Reload; a refusal says what is safe ("We couldn't save
  that. Nothing was changed."); a support visit sees the banner and every Edit disabled.

### Actions (`src/app/(console)/console/content/actions.ts`)
`saveAnnouncement`, `endAnnouncement`, `deleteAnnouncement`, `saveMenu`, `saveContact`, `savePage`, `addPage`,
`hidePage`, `saveQuestion`, `moveQuestion`, `removeQuestion`, `undoContent`. Each: `asMember(CAN_BUILD, …)`; inside the
transaction `contentSaver(role, hasOwnerIn(tx), supportSessionId)` refuses in words; the per-shop limiter
`LIMITS.contentSave` (30 a minute a shop, Postgres limiter, fail closed); Zod with the domain schemas; a conditional
update `where tenant_id = … and id = … and version = $seen` (0 rows → stale, in words, with who and when); `previous :=
value`, `version + 1`, `updated_by := auth user`; one `audit_events` row (actor_kind `member`, action
`content.save|end|delete|undo`, target the row id, detail the kind, key and field names only, never the words); after the
commit, the purge: `site_content` saves through `refreshContent(tenant)` (a `refreshSoldOut`-style limiter: once per
30 s per shop, one trailing purge, never dropped), page and FAQ saves purge `shop:<t>:pages` only. Links are checked
with `shopPath` (relative shop paths only); images in pages with `acceptedBase(…, 'theme')` as today.

### The move (one release)
- **Migration `NNNN_site_content_move.sql`** (renumbered at merge; applied by the orchestrator before the push):
  `app_move_content()` (security invoker, revoked from every role, run once at the end of the migration and again by
  the orchestrator right after the push for shops whose live publish changed in between; `on conflict (tenant_id,
  kind, key) do nothing`). For each tenant: the **live** revision as `liveOf` derives it (the newest publish of each
  version, newest first, minus withdrawn versions; joins on `(tenant_id, revision_id)`), then its layer's
  `settings.announcement` (an entry, no dates), `menus.main|footer|tabs` (each set one a row), `contact`. Labels and the
  line are re-checked by a SQL twin of the old `PLAIN` pattern; a failing item is dropped and named in the notice.
  Drafts are not copied: where the shop's draft layer differs in those three parts, one Inbox notice (`type
  needs_you`, `source_kind content`, href `/console/content?tab=menus`) "Your unpublished menu changes were not moved."
- `shop_pages`: the FK `shop_pages_live_publish` is dropped; `draft := live` for pages that are live (a page whose draft
  differed is named in the same notice); a page never published becomes a hidden page (`live` null, nothing shown).
  `live_publish_id` stays, unused, until a later migration drops it with the function.
- **A parity int test** seeds shops (two versions, a withdrawn one, Undo, a draft) and checks the SQL picks the same
  revision as `liveOf` and copies exactly its parts (`site-content-move.int.test.ts`), as `app_trial_recompute`'s.
- **The Look stops writing them:** `LayerSchema` drops `menus` and `contact`, `SettingsSchema` drops `announcement`
  (stored layers keep the keys; Zod strips them on read), `layerProblems`, `carryOver`, `saveLookAction`, `cleanImages`
  and `page-readiness.ts` stop touching them; `preparePages`/`undoPages`/`discardPages` leave `publishRevision`, Undo
  and Discard; Look's thumb (`thumb.tsx:15`) draws the content bar. Released manifests keep `announcement: null`
  (manifests never change); `resolveTheme` ignores it.
- **The Look's panels become links:** the customizer's Menus tab, Style › Header's bar, the Contact page and each page
  in the page picker show one row "Edit in Content ›" (a full link to the tab). The preview still draws the live
  content.
- **The proof:** `src/domains/content/__tests__/no-layer-readers.test.ts` reads every file under `src/` (comments
  skipped, CLAUDE.md "a gate must not match its own documentation") and fails on `layer.menus`, `.menus` off a layer or
  `ResolvedTheme`, `settings.announcement`, `layer.contact`, `readMenus(`, `readContact(`; it runs against the file
  that describes it.

## Decisions (taken in this plan, within the spec)
1. The bar's written entries: the one that **started last** shows when several are live (a sale's bar replaces a
   standing one without deleting it). Offer first (owner decision 7).
2. The bar keeps its colour (Paper · Tint · Ink) on the entry: it moves with the text, so no store's bar changes.
3. Menus keep today's names and limits (`main`, `footer`, `tabs`; 3 levels, 12 items, 5 tabs, labels 40).
4. A page or menu saves with one explicit Save (shoppers see it at once: frata-design-language Phase 1 "never autosave
   what shoppers see"); entries and questions save from their dialog.
5. The move's lost drafts are told once, as an Inbox notice, never by reading the old layer again.
6. Pages: save is live; a never-published page becomes Hidden; `live_publish_id` dropped later with the function.

## Owner questions
1. **A partner after handover:** V1 lets a partner save only before handover (the spec's switch, "Edit content live" in
   Settings › People, needs ADR-0015's grants from lane C). The Inbox line for a partner's save comes with that switch:
   before handover there is no owner to tell. Ship V1 so, and add the switch and the Inbox line after lane C? (Suggested: yes.)
2. **The preview pane** drawn on the approved mockup needs the Storefront API's preview token (V2). V1 shows "View
   store" (a new tab) instead. Accept? (Suggested: yes; a save is live within 60 s.)
3. **Staff** see Content read-only (spec: "Staff read only"). Should staff edit the FAQ and the bar, as they edit
   products? (Suggested: no for V1.)

## Design review (frata-planning § 3; the spec's review holds, these are this phase's own)
- **UI/UX:** one primary per dialog (Save); states per tab: empty (No announcement yet · Add), one, full ("3 of 3"),
  scheduled, live, behind the offer, ended, stopped, read-only (staff, partner after handover), support visit, stale,
  refused, saving, phone. Constraints over refusals: links from a picker, dates from a picker, counters. Undo 8 s.
- **Tenancy:** § `site_content`; tenant only from `requireMember` or the host; the move per tenant joins on
  `(tenant_id, revision_id)`; no `frata_admin` grant; `updated_by` never leaves the console.
- **Modularity:** domain pure; one read seam; actions in one file; components under `content/`; Look imports nothing
  from content but the link.
- **SSOT:** one row per fact; the bar's order once (`bar.ts`); state from dates; menus' schema moved, not copied.
- **YAGNI/KISS:** no drafts, no preview token, no placements, no seasons; a closed set of three kinds.
- **Performance:** (a) shop frame: theme ‖ content ‖ offer in one `Promise.all` (net −1 serial read); Content page:
  one transaction, rows + look settings + people names in `Promise.all`; (b) EXPLAIN `site_content (tenant_id, kind,
  key)` index scan at the 10× seed; (c) entry ≤ 100 kB worst case (3 × 32 kB menus + bar + contact), size test; (d) no
  shop HTML growth beyond today's menus; (e) a save purges `shop:<t>:content` (every page, ≤ once per 30 s, trailing),
  a page save `shop:<t>:pages` only; (f) no new shop JS; Content's console JS within 150 kB (dialogs load on open);
  (g) nothing preloaded.
- **Reliability:** no outbound call; a failed save says nothing changed; the trailing purge never drops the last save.
- **Security:** `contentSaver` inside the transaction; support refused by its session; Zod + `plainText` caps; links
  shop paths only; images by `acceptedBase`; limiter fail closed; audit with field names, previous value in the row;
  merchant words render as React text, never HTML.
- **Motion:** § Feedback toasts; Dialog/sheet; Segmented; no new motion.
- **Unit economics:** none: data writes, no model, sandbox or build.
- **Blast radius:** `resolve.ts`, `layer.ts` (carryOver, schemas), `site.ts`, `shell.tsx`, `_frame.tsx`, previews,
  policies page, share card, `thumb.tsx`, the customizer (`editor.tsx`, `theme-form.tsx`, `pages-panel.tsx`,
  `page-form.tsx`, `menus-form.tsx`), `look.ts` (publish/undo/discard), `pages.ts`, `page-readiness.ts`,
  `page-actions.ts`, `refresh.ts`, `storefront.ts` (`shopCached` union), the console layout (nav), notices CHECK.
