## Goal
Ranked problems 1 (COD/RTO: a merchant finds the orders to act on, e.g. COD to Bihar this week, in two taps) and 3
(catalogue operations: a product found as you type). Measure: the time from Orders to a filtered view; search results
within 150 ms of the last key plus one round trip (p95 under 400 ms at the 10× seed, 150 k orders in a shop); parity at 1280 and 390.

## Scope
**In:** Orders' filter bar with chips (Payment, State, Placed, Total), "+ Filter" with values and their counts, Clear
all, all of it in the address; saved views as tabs with counts (Save, Rename, Remove), shared by the whole team;
instant search on Orders (number, name, any 4+ phone digits, AWB) and Products (name, SKU, tag) with the
match marked and "No order matches 9845"; quick look on Orders (400 px panel, ↑↓, Esc, Open order); the phone's
filter sheet with "Show N orders"; the phone's two-line order rows and the "N to confirm" chip by the title; Products'
tabs above the search and "More" as a ghost button (N1 Deviations).

**Out (owner, 2026-11-13):** Risk, Source and Tag as filters (no SQL form or column today; they come back when the
owner asks). ⌘K is N1b. Filters on Products beyond its status tabs and sort (they exist, PR·1). "Low · 2" (no
threshold setting yet).

## Order of work
**N1c·1 — The filter engine (pure) and its SQL** (built: `src/domains/orders/filters.ts`, `filterSql`)
1. `parseFilters(params)` keeps only `pay` (cod · paid · unpaid), `st` (GST codes → names on the closed `STATES` list,
   ≤ 10, matched against `orders.state`, the delivery state as stored; an order whose state is spelt otherwise is in no
   State filter, and the value list shows only names on the list), `placed` (today · 7d · 30d, or IST `from`/`to` days),
   `min`/`max` (whole rupees in the address, paise inside via `fromRupees`). One canonical form (`filterQuery`) for the
   address, the rows route and a saved view: no second encoding.
2. `paymentKind(o)` (pure, `order-state.ts`: cod · paid · unpaid) and `paymentKindSql` beside `currentMethodSql`, with a
   case in the parity int test; the Payment column and the `pay` filter both read them. `filterSql` uses only bound
   parameters, never `sql.raw` of a value; `placed` compares `placed_at` with IST bounds as timestamptz (a test that
   the SQL never casts `placed_at` to a date, which would lose `orders_tenant_placed`). Placed is the one indexed
   filter; a rare filter on All scans the shop's orders (measured 89–132 ms at 150 k; inside budget at today's sizes).
3. `listOrders` and `queueCountsWith` take the filters (counts under the filters: "9 of 300 orders");
   `queueCountsWith` gets `set local jit = off` (its in-flight count: 700 ms with JIT, 127 ms without, speed review).
4. Values with counts for "+ Filter": `GET /console/orders/filter-values?field=` — `field` a closed enum (pay · st)
   mapped to fixed SQL in `order-predicates.ts`, anything else 400; its own `withTenant` with `set local
   statement_timeout = '800ms'` and `jit = off` (a named exception to the 100 ms query budget, written in
   frata-architecture § Speed); a timeout shows the values without counts.

**N1c·2 — Saved views (one migration)**
5. `saved_views (tenant_id uuid not null references tenants on delete cascade, id uuid, tab text (a QueueTab), query
   text ≤ 400 (the canonical filters; never `q`), name text 1–40, created_by uuid (the auth user, no FK: support
   visits write too), created_at, updated_at, removed_at)`; unique `(tenant_id, lower(name)) where removed_at is null`.
   No `surface` column: one list has views (YAGNI). Grants to `frata_app`: select, insert, delete, update (name,
   updated_at, removed_at) only; revoked from anon, authenticated, service_role; `frata_admin` none; RLS and the
   `tenant_rows` policy (`using` and `with check` on `app_current_tenant()`) in the same migration. Proof
   `n1c-saved-views` in `scripts/verify/tenancy.sql`: the 11 assertions of the tenancy audit (policy shape, exact
   grants and column grants, no grant to the other roles, A sees only A, cross-tenant insert 42501, update/delete of
   B's row by id 0 rows, no tenant → 0 rows, same name in A and B, case-different duplicate 23505, CHECKs, indexes lead
   with tenant_id).
6. Actions `saveView`, `renameView`, `removeView`, `restoreView` through `asMember(ANY_MEMBER)` (owner, admin, staff,
   partner: who sees Orders; any of them may rename or remove the team's views; the accountant never). Zod: name trimmed,
   NFC, 1–40, no control or bidi-override characters; id `z.uuid()`; the query re-parsed and stored canonical. The cap
   of 20: `pg_advisory_xact_lock(hashtextextended(tenant || ':views', 0))`, count, insert, one transaction; 23505 →
   "A view with that name exists" (not logged). Rename and remove `where tenant_id and id`; 0 rows → "View not found".
   Remove sets `removed_at`; Undo is `restoreView` by id (a name taken since → the same refusal). Replies: id, name, tab,
   query only. On read a view's href is rebuilt from `parseFilters(query)`, never the stored text.
7. View tabs after the built-in ones: name, count, a menu (Rename, Remove with Undo). "+ Save view" when filters are on
   and differ from every view. Counts: one statement (`count(*) filter (where …)` per view over an `offset 0`
   subquery of the derived state, `jit = off`, `statement_timeout 800ms`, measured 189–212 ms at 150 k) in its own
   `withTenant`, streamed behind Suspense, never in `queueCounts`' transaction.

**N1c·3 — Instant search**
8. `parseOrderSearch` decides the arm, so one search never ORs a slow test with a fast one: digits only → the number
   or the phone containing them (any 4+ digits, as drawn; measured 95 ms at 150 k as a scan under RLS, no new index);
   an AWB shape (letters and digits, 8+) → `shipments (tenant_id, tracking_number)` exact (new index; 0.12 ms) joined
   to its order, plus the number; text → the name ILIKE (escaped), with `statement_timeout`. No window count: fetch
   51, a 51st row means "50+" and shows Older.
9. `GET /console/orders/rows?…` (the page's own canonical query): `requireMember(ANY_MEMBER)`, one `withTenant` with
   list + prefix + `riskFactsWith(tx, …)` in `Promise.all` (1 transaction, 4 statements; no counts), `statement_timeout
   1500ms`; `q` capped at 60; replies the `QueueRow` fields (no phone except the matched text, no cost) plus `matched:
   { field: 'number' | 'name' | 'phone' | 'awb', text }` for the mark. A per-member limit `LIMITS.ordersReadMember`
   (600 / 10 min; fails open). Logs `errName` only, never `q`. The row builder moves to `orders/_components/rows.ts`
   (one copy for page and route).
10. One client island (`orders/_components/orders-list.tsx`) owns the rows, the pager, the empty state, the list's label
    and which tab is current, all fed by the route; the box sends 150 ms after the last key, aborts the one in flight,
    and writes `?q=` with `history.replaceState`. Enter and Back render the page; `SearchField` carries every filter
    param (`filterParams`), not only the tab. The match is marked with `<mark>` from `highlight()`
    (`src/domains/text/highlight.ts`, pure: `{ text, hit }[]` from folded `indexOf`, never a RegExp from `q`, rendered
    as React text). A phone match shows the phone as a second line under the name, as drawn.
11. Products: the same island pattern over a `GET /console/products/rows` route reading `listQuery` (name, SKU, tag;
    `escapeLike` from one place, the two restatements in `catalogue.ts` removed).

**N1c·4 — Quick look**
12. Space on a focused row (in `SHORTCUTS` and the KeySheet; preventDefault) or the row's Quick look button (desktop)
    opens a 400 px panel from the right over the list, which keeps its scroll; ↑↓ move it, Esc closes and gives focus
    back to the row, "Open order" goes to the page. `GET /console/orders/[number]/peek`: `requireMember(ANY_MEMBER)`;
    the order by `(tenant_id, number)` (another shop's number: the same 404 as none); 1 transaction, 3 statements in
    `Promise.all`: the order's named columns, its lines (name, size, qty, unit price, never `unit_cost`), its last
    three events; an erased order reads as erased. A per-member limit `LIMITS.peekMember` (120 / 10 min, fails
    closed). A unit test that the reply's keys are exactly the allowed list.

**N1c·5 — The phone**
13. Orders rows on a phone as drawn: line 1 "KS-5006 · Sneha" and ₹ at the right; line 2 the place and the status
    chip; a warn "43 to confirm" chip by the title. "Filters" opens the sheet (Dialog as a sheet): Payment, State,
    Placed, Total; "Show N orders" from the rows route with `count=1` (the count only, debounced).
14. Products: tabs above the search; "More" as a ghost button (`Menu` gains `variant`, today's look the default).

**Every route** (rows, filter-values, peek, products rows): `export const dynamic = 'force-dynamic'`; `Cache-Control:
private, no-store` and `nosniff` on every reply, errors included; no `cache()`; the tenant only from
`auth.membership.tenantId`. Accepted: partial names and phone digits typed in the box reach request logs as `?q=`, as
the page's `?q=` already does today (same origin, the referrer policy keeps them off other sites).

## Design review
- **UI/UX:** chips read as a sentence; × on each (24 px target, its name "Remove Payment is COD"); "+ Filter" is a Menu
  of fields then a list of values with counts (checkboxes for sets, two fields for ranges); Clear all. States: no
  match ("No order matches these filters" with Clear all), counts unavailable (values without counts), loading (the
  list dims, Neel § Motion), error (Panel). Keyboard: chips and menus by Tab; "/" focuses search (existing); Space
  quick look; ↑↓ in the panel; Esc closes. Live region: "9 orders" after a filter changes. Rule 0: no helper text.
- **Tenancy:** one new table with grant, RLS and policy in its migration; every read through `src/lib/queries/` in
  `withTenant`; the tenant from `requireMember` (the routes too); a saved view's query is re-parsed, never trusted.
- **Modularity:** filters pure in `src/domains/orders/filters.ts`, highlight in `src/domains/text/`; SQL in
  `order-predicates.ts`; reads in `src/lib/queries/orders.ts` and `saved-views.ts`; actions in `orders/actions.ts`;
  UI in `src/components/data/filter-bar.tsx` and `quick-look.tsx` (generic), Orders' wiring in its `_components/`.
- **SSOT/DRY:** a filter is parsed once (`parseFilters`), turned into SQL once (`filterSql`), into words once
  (`chipsFor`); rows built once (`rows.ts`); counts from the same predicates as the list.
- **YAGNI/KISS:** no filter engine for other lists until a second list asks; no personal views (the drawn ones are the
  team's); no saved sort.
- **Scalability / performance (speed review, measured at 150 k orders under RLS):** Orders page: auth + 3 parallel
  transactions (counts 3 statements; list ‖ prefix; view counts streamed) then risk (2): ≤ 9 statements, none
  repeated. A keystroke: auth + 1 transaction, 4 statements. JIT off where a count scans. No index on an expression
  (not leakproof under RLS: never used).
- **Reliability:** no outbound call; a failed count shows no count, never a wrong one.
- **Security (security review):** four actions through `asMember(ANY_MEMBER)`; four GET routes, each its own
  `requireMember`, rate-limited, no-store; replies of named fields only; see each step.
- **Motion:** the panel slides 200 ms (reduced: none); chips appear without motion.
- **Unit economics:** none.
- **Blast radius:** `listOrders`/`queueCounts` callers (Orders, Home's counts, nav pill — the pill and Home keep no
  filters), Queue (keys j/k/c/h/z), 40-queue, 20-orders-count, 49-ship, 79-products-list, 90-ux; the Products list.
