## Goal
Ranked problems 1 (COD/RTO: a merchant finds the orders to act on, e.g. COD to Bihar this week, in two taps) and 3
(catalogue operations: a product found as you type). Measure: the time from Orders to a filtered view; search results
within 150 ms of the last key plus one round trip (p95 under 400 ms at the 10× seed); parity at 1280 and 390.

**In:** Orders' filter bar with chips (Payment, State, Placed, Total), "+ Filter" with values and their counts, Clear
all, all of it in the address; saved views as tabs with counts (Save, Rename, Remove), shared by the whole team;
instant search on Orders (number, name, any 4 phone digits as the last 4, AWB) and Products (name, SKU, tag) with the
match marked and "No order matches 9845"; quick look on Orders (400 px panel, ↑↓, Esc, Open order); the phone's
filter sheet with "Show N orders"; the phone's two-line order rows and the "N to confirm" chip by the title; Products'
tabs above the search and "More" as a ghost button (N1 Deviations).

## Order of work
**N1c·1 — The filter engine (pure) and its SQL**
1. `src/domains/orders/filters.ts` (pure): `parseFilters(params)` → `{ pay?: ('cod'|'prepaid'|'unpaid')[], state?:
   string[] (≤ 10, from the GST state list), placed?: { from?: ISO date; to?: ISO date } | 'today'|'7d'|'30d', total?:
   { min?: paise; max?: paise } }`, `filterHref`, `chipsFor` ("Payment is COD", "Total ₹500–₹2,000"), `sameFilters`.
   Rejects anything else (unknown keys dropped, ranges clamped, dates in IST). Unit-tested.
2. `src/lib/db/order-predicates.ts`: `filterSql(f, now)` from the same predicates the rows use (`currentMethodSql`,
   paid_at, `orders.state`, `placed_at` in IST, `total`). `listOrders` and `queueCounts` take the filters, so a tab's
   count is its count under the filters (the drawn "9 of 300 orders").
3. Values with counts for "+ Filter" (`filterValues(tenantId, field, tab, filters)`): one grouped query for the field
   asked for, run when its menu opens (a light route, `GET /console/orders/filter-values`), inside the tab and the other
   filters, in a savepoint with `statement_timeout 800ms`; a timeout shows the values without counts.

**N1c·2 — Saved views (one migration)**
4. `saved_views (tenant_id, id, surface 'orders', name text 1–40, query text ≤ 400 (the filters' canonical href),
   created_by, created_at, updated_at)`, unique `(tenant_id, surface, lower(name))`, ≤ 20 per surface (a CHECK cannot
   count: the action counts in the same transaction, `for update` on the tenant row). Grant to `frata_app`, RLS and the
   policy in the same migration; `verify:tenancy` proof `n1c-saved-views`.
5. Actions `saveView`, `renameView`, `removeView` (Zod: name, query re-parsed by `parseFilters` and stored canonical,
   never as typed; roles: owner, manager, staff — the same as who can see Orders). A view tab: its name and count;
   its menu (Rename, Remove, with Undo). "+ Save view" appears when filters differ from every tab.
6. Counts for saved views: one statement, a `count(*) filter (where …)` per view (≤ 20), in the same transaction as
   `queueCounts`.

**N1c·3 — Instant search**
7. A light route `GET /console/orders/rows?q=&tab=&f=` returning the page's rows (the row builder moved out of
   `orders/page.tsx` into `orders/_components/rows.ts`, one copy for the page and the route). The search box sends
   150 ms after the last key, cancels the one in flight (AbortController), and writes `?q=` with
   `history.replaceState` (no page render per key). Enter or Back renders the page as today.
8. Matches: the order number; the name (ILIKE, escaped); 4 digits → the last 4 of the phone (expression index
   `(tenant_id, right(phone, 4))`), 5+ digits → contains, as today; an AWB → exact on `shipments (tenant_id,
   tracking_number)` (new index, same migration). The matched part is marked (`<mark>`, from `highlight()` in
   `src/domains/text/highlight.ts`, pure). Totals cap at "50+" (no window count beyond the page).
9. Products: the same box over name, SKU and tag through its existing list query (`listQuery`), 150 ms, replaceState.

**N1c·4 — Quick look**
10. Space on a focused row (or the row's "Quick look" button, desktop only) opens a 400 px panel from the right over
    the list, which keeps its scroll; ↑↓ move it to the next row, Esc closes and gives focus back to the row, "Open
    order" goes to the page. A lean read `peekOrder(tenantId, number)`: lines (name, size, qty, price), address, phone,
    payment, state, the last three events. No cost field (check-client-bundle). Route `GET /console/orders/[n]/peek`.

**N1c·5 — The phone**
11. Orders rows on a phone as drawn: line 1 "KS-5006 · Sneha" and ₹ at the right; line 2 the place and the status
    chip. The title row carries a warn "43 to confirm" chip. A "Filters" button opens the sheet (Dialog as a sheet):
    Payment, State, Placed, Total; "Show N orders" counts before the person looks (the rows route with `count=1`).
12. Products: tabs above the search; "More" as a ghost button (Menu `variant="ghost"`).

## Design review
- **UI/UX:** chips read as a sentence; × on each (24 px target, its name "Remove Payment is COD"); "+ Filter" is a Menu
  of fields then a list of values with counts (checkboxes for sets, two fields for ranges); Clear all. States: no
  match ("No order matches these filters" with Clear all), counts unavailable (values without counts), loading (the
  list dims, Neel § Motion), error (Panel). Keyboard: chips and menus by Tab; "/" focuses search (existing); Space
  quick look; ↑↓ in the panel; Esc closes. Live region: "9 orders" after a filter changes. Rule 0: no helper text.
- **Tenancy:** one new table with grant, RLS and policy in its migration; every read through `src/lib/queries/` in
  `withTenant`; the tenant from `requireMember` (the routes too); a saved view's query is re-parsed, never trusted.
- **Modularity:** filters pure in `src/domains/orders/filters.ts`, highlight in `src/domains/text/`; SQL in
  `order-predicates.ts`; reads in `src/lib/queries/orders.ts` and `saved-views.ts`; actions in `orders/actions.ts`;
  UI in `src/components/data/filter-bar.tsx` and `quick-look.tsx` (generic), Orders' wiring in its `_components/`.
- **SSOT/DRY:** a filter is parsed once (`parseFilters`), turned into SQL once (`filterSql`), into words once
  (`chipsFor`); rows built once (`rows.ts`); counts from the same predicates as the list.
- **YAGNI/KISS:** no filter engine for other lists until a second list asks; no personal views (the drawn ones are the
  team's); no saved sort.
- **Scalability / performance:** at the 10× seed (50 k orders a shop): the list ≤ 4 statements in one transaction;
  filter values one grouped statement with a timeout; saved-view counts one statement; search uses the phone and AWB
  indexes and the placed index for order; no page render per key. Speed reviewer to EXPLAIN each at the 10× seed.
- **Reliability:** no outbound call; a failed count shows no count, never a wrong one.
- **Security:** three actions (check:actions), Zod-capped; two GET routes behind `requireMember` returning only what
  the page shows (no costs); `q` capped at 60, the query string at 400; `<mark>` built from text nodes, never HTML.
- **Motion:** the panel slides 200 ms (reduced: none); chips appear without motion.
- **Unit economics:** none.
- **Blast radius:** `listOrders`/`queueCounts` callers (Orders, Home's counts, nav pill — the pill and Home keep no
  filters), Queue (keys j/k/c/h/z), 40-queue, 20-orders-count, 49-ship, 79-products-list, 90-ux; the Products list.
