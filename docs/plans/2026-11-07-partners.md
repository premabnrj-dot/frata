## Review findings (2026-11-07) and what the plan does about each

architecture-reviewer, tenancy-auditor and unit-economics-reviewer ran on this plan. V1 (tokens and
pictograms) had started before they reported. It touches no data, and their findings did not change it.

| Finding | Fix in this plan |
|---|---|
| A handover invite would be claimed silently at sign-in (no Accept), or burned when the shop has an owner | `app_claim_invites` skips owner invites on partner-linked shops in its WHERE. New `app_my_handovers(uid)` + `app_accept_handover(uid, invite)`: locks the tenant, refuses if an owner exists, the email is not the caller's confirmed email, or the caller is the partner. After sign-in, a pending handover routes to `/handover` |
| Handover race / two owners / partner hands to self | `app_handover_invite(tenant, uid, email)` locks the tenant row, re-checks the partner member, the active link, that the link is the caller's own partner row, and that there's no owner. It refuses the caller's or any member's email and revokes the earlier open owner invite. One open owner invite per tenant (unique partial index) |
| Settings are one CAN_MANAGE guard; widening it would open payments | Each settings section declares `editors`, read by the page, `saveSection` and the brand upload. All shop-settings sections are `CAN_BUILD`. Online payments stays owner, the address stays CAN_MANAGE, shop open/close stays CAN_MANAGE |
| Partner in ANY_MEMBER sees orders and profit (shopper details, margins) | **Kept: the owner approved "products, orders, settings and the look"** (screen 8). The accept screen says "orders" plainly. Raised in the hand-back as a call the owner can reverse by removing partner from ANY_MEMBER |
| `app_shop_people` must not take a tenant id | `app_shop_people()` reads `app_current_tenant()`, inside `withTenant` after `requireMember(CAN_MANAGE)` |
| Remove partner: support mode acts as owner | `app_remove_partner(tenant, uid)` requires a `members` row with role owner (a support visit has none). It sets removed_at, deletes the member, and revokes the partner's open invites, in one transaction, audited |
| A removed partner keeps the owner's email, plan and host in Clients | `app_partner_clients` returns only the name and dates for removed links |
| Approved = approved_at and not declined; the cap counted under the lock | `app_partner_create_shop` uses the same `create_shop:` advisory lock and counts unopened links (`share_starts_at is null and removed_at is null`) |
| Terms in TS and SQL | `PARTNER_TERMS` passed as parameters (bps, months, days, cap). The CHECKs bound them |
| Window restarts on reopen | `share_starts_at`, written once by a trigger on the first `published_at` |
| Example over-promises | Computed in `src/domains/partners/example.ts` from plan rows. Shown as "Example". Assumptions in an (i) tip. Hidden when plans don't load |
| Definer wrappers would fail check:tenant in queries/ | `src/lib/db/partners.ts` (db scope). Only the partner_links read for People is in `src/lib/queries/` |
| Switching stores in another tab | `TenantCheck` runs for anyone with 2+ places to go, not only staff |
| Migrations | 0022 (drizzle-kit, tables) and 0023 (custom: grants, RLS, functions), both in the journal |
| Shell tag | `tag?: 'STAFF' \| 'PARTNER'` replaces `staffTag` |
| Rule 20 "no illustrations in empty states" | Superseded for the website and the partner workspace only (owner, 2026-11-07). The console and Admin keep rule 20 |
| Voice gate noise | Skips `//`, `/*` and `*` lines, has an allow file, scans .ts and .tsx string literals, never `.claude/`. It catches banned words only. "Passages" stay a review item |
