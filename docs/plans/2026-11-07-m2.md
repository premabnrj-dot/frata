## Review findings

### tenancy-auditor (2026-11-07): fix in the plan before step 1
| Sev | Finding | Fix (binding on the build) |
|---|---|---|
| HIGH | Embedded Signup hands `waba_id`/`phone_number_id` to the **browser**: a forged id could claim another shop's number | The server reads both ids from the exchanged token (`debug_token` granular scopes → `/{waba}/phone_numbers`) and ignores the client's. Partial unique index on open rows for `phone_number_id` and `waba_id`. e2e with a forged id |
| HIGH | Webhook routing under-specified | `app_tenant_for_wa(pnid)` and `app_tenant_for_waba(id)`: open rows only, format `^[0-9]{5,20}$`, `search_path=''`, return tenant_id only, EXECUTE revoked from public/anon/authenticated. Route and store **per change** (one POST batches several entries). Unknown id: store nothing, answer 200. Proofs: duplicate open ids fail; closed A + open B routes to B; closed alone → nothing; bad format → nothing |
| HIGH | Blob store is public and tenant paths are already visible | Private store, or a 128-bit random name under `tenants/<id>/wa/`. The URL never reaches a browser. Served by `/api/console/media/[messageId]` (`requireMember`, path looked up by message id inside `withTenant`, partner check, `private, no-store`). `PATH_SHAPE` keeps refusing `wa/` |
| HIGH | Inbox visibility is app-only (RLS can't tell roles apart) | One `canSeeChats(membership, settings)` read by every inbox query, action, the polling endpoint, the media route and the `customer.side` slot. e2e: a partner is refused at each. Support sends carry actor `support` |
| MED | Cross-tenant references | Composite FKs `(tenant_id, x_id)` on contacts, conversations, messages (and `order_id`), notes, reads, presence, consents, `assigned_to` → members. Proof: A can't point at B's conversation |
| MED | Outbox sender | Payload holds no token and no pnid. The sender opens `withTenant` and reads the **open** connection at send time. `seal(token, tenantId, 'wa_token')`. Drop `pin_enc` unless needed |
| MED | Button replies | Find the order by `context.id` (the replied-to wamid) → `messages.order_id` inside the routed tenant. Never from payload text |
| MED | Webhook key | `whatsapp:<tenant>:<pnid>:<wamid>:<status>`, so delivered and read for one wamid don't collapse into one row |
| MED | frata_admin | No grant on any communication table. Proof: admin read raises |
| LOW | Modules plan text | Platform tables use a select policy, like plans' `catalogue_read` (not a definer). Proofs: frata_app can't write `tenant_addons`, `addon_prices` or `module_pauses`, or B's `tenant_modules`; a second open switch row fails; admin inserts but can't update `tenant_addons`. A pause revalidates every shop's tag |
| LOW | Polling endpoint | Calls `requireMember` itself; tenant from the membership; never cached; logs no bodies or phones |
| LOW | Checkout consent | The contact's tenant comes from `tenantForHost()`, never a form field |

### unit-economics-reviewer (2026-11-07), computed with orderProfit() on illustrative shapes
- **Add-on prices (hypotheses for the owner):**
  - True Profit ₹999/mo on Launch, included from Growth. The order-level profit stays in every plan;
    breakdowns are the add-on.
  - Reviews & UGC ₹499 (Judge.me is free/$15).
  - Assisted DM orders ₹499 or included (they already pay the delivered-order fee).
  - Marketplace export ₹1,499 as a placeholder (no competitor price found).
- **Seats:** keep 3 / 10 / 25; an extra seat ₹299/mo (Wati +$39). The limit's real job is to cap polling load.
- **WhatsApp per order:** 5 × ₹0.1150 = ₹0.68 with GST per COD order, **₹0.81 per delivered** (the spec is
  corrected). Confirmation pays for itself many times over (a 0.07–0.12 pp RTO cut covers it). But the app
  stack sells it too (Engage ₹2.49/order), so Frata's own gain is about ₹1.81 per COD order until a deeper RTO
  cut is proven.
- **Risk:** at the illustrative Launch shape, Frata Launch (₹3,726.50) costs ₹661 more than the cheapest
  Shopify stack (₹3,065.45) and wins only once a checkout app is in that stack. The pricing page must lead
  with the bundle.
- **Frata's cost:**
  - Blob media is negligible with retention and a size cap.
  - **Polling dominates:** about 187k requests per seat a month at 4 s (~₹43). Hence visible-tab-only polling,
    slower when idle, and one cheap "inbox changed at" read (the spec is corrected).
- **Hypotheses rows** go into frata-unit-economics when the owner confirms the prices.

### architecture-reviewer (2026-11-07)
| Sev | Finding | Fix (binding on the build) |
|---|---|---|
| BLOCKER | Status webhooks reuse the wamid, so `delivered`/`read` dedupe away. One POST batches many items | Key `whatsapp:<tenant>:<pnid>:<wamid>:<status>`. One `webhook_events` row **per item**, not per POST |
| MAJOR | Customer confirm path | `order_events_who` CHECK rewritten for actor `customer`, with a message reference. The reply's `context.id` must be our sent wamid and the sender's phone must match the order. Compare-and-set (`confirmed_at is null and cancelled_at is null`). "Asked to cancel" is an `order_events` row. `processEvents` claims with `SKIP LOCKED`. **Owner call: may a reply confirm a High-risk order?** ("risk advises, never acts") |
| MAJOR | Duplicate billed sends on timeout (Meta has no idempotency key) | Send `biz_opaque_callback_data` = our message id and match statuses on it. A status that arrives before its wamid is stored is left unprocessed, not failed. The spec's "retries are safe" is withdrawn |
| MAJOR | WABA-keyed webhooks | `app_tenant_for_waba` (also tenancy-auditor). Partial unique on open connections |
| MAJOR | The outbox sweep runs outside a tenant | Group claimed rows by tenant and call `shopModules` inside `withTenant` (no SQL copy of "usable"). A **pause defers** (`next_attempt_at`), never kills. "Off" cancels queued rows in the switch's own transaction. Size `claimDue` for festive volume (25/min ≈ 36k/day is too low) |
| MAJOR | Storefront cache vs expiring trials | Cache the facts, derive with `now` at render; `revalidate` bounded by the next expiry; a `module:<key>` tag for pauses |
| MAJOR | `check:modules` would fail on the first module | An explicit allow-list of hook points: sender registry, webhook routes, slots, nav, checkout consent. `asModule(` accepted by check-actions. Retire `FEATURES` and `canUse` (one list: the registry) |
| MAJOR | Contacts vs orders | One phone normaliser in `src/domains` and an index on the matching form. A merge rule when a BSUID contact gains a phone. **`consents` keyed on (tenant, phone) as a core DPDP table**, not a module table |
| MAJOR | Media within 5 min | Store the media id; a fresh URL can be fetched again with it (retention ~30 days, to verify) |
| MAJOR | Polling cost | 4 s only on an open, visible thread; 15–30 s on the list; stop when idle (also unit-economics) |
| MAJOR | Phase order | C1 → C2 → C3 (done above). Template creation per merchant goes through the outbox. Template approval takes up to 24 h, so the first day misses the 5-minute measure: say so in the measure |
| MINOR | YAGNI | Defer typing presence, snooze, `dependsOn`, and five of the seven slots. `customer.side` lives inside the module |
| MINOR | One key for every secret | A key id or a per-purpose HKDF info in `seal()`. Don't store the PIN. A "Reconnect" needs-attention state (token lifetime [U]) |
| MINOR | Retention | Purge `webhook_events` payloads after processing |
| MINOR | Coexistence in India is [S] only | Confirm before the mockup |
| MINOR | Composer | No typing indicator on open; add `z`/`?` to the keys |
| MINOR | Inline code exchange on connect | Allowed with `fetchWithTimeout`; written down as the ADR-0006 exception |
