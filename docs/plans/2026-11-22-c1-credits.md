## Rules this phase holds
- **Money is integer paise; credits are integers.** Prices are one table in `src/domains/studio/prices.ts`:
  pack 1,99,900 paise for 100; Studio 2,99,900 with 150 a month; Studio Plus 9,99,900 with 500; a typed credit 2,000.
  GST 18% from billing's rate (`src/domains/billing/gst-rate.ts`), CGST+SGST or IGST by Frrata's and the buyer's state.
  ₹1,999 → ₹2,358.82; ₹2,999 → ₹3,538.82; ₹9,999 → ₹11,798.82. AutoPay maximum: Studio ₹3,600, Plus ₹12,000 a debit (RBI
  e-mandate limit without extra authentication ₹15,000, frata-integrations § Merchant billing, checked 2026-11-08).
- **A credit balance is derived, never stored.** Balance = the sum of `partner_credit_entries` by lot, live lots only.
- **A payment is believed only from the verified webhook or a server-side fetch** (`fetchPayment` / `orderPayments`),
  matched to OUR attempt row by gateway order id, amount, currency and test mode; never a partner id or amount from the
  payload or the browser. Checkout's handler result only triggers the server-side fetch.
- **A call to Razorpay is an attempt row before it is a request** (ADR-0008 pattern; no outbox: a purchase has no
  tenant). Receipt = the attempt's id; a retry first asks `orderByReceipt`. A recurring debit is claimed once ever
  (the `claimBillingAttempt` pattern) and never resent.
- **Test keys only** in every test and flow (`billingGatewayIsTest()`); a test-mode purchase gets a TEST invoice
  ("Test — not a tax invoice") whenever `frrataSeller().test`; a live key never settles a test attempt or the reverse.
- **No Frrata role reads these tables** (P2's pattern, frata-architecture § A partner's own records): no grant to
  `frata_app`, `frata_admin`, `frata_builder`; RLS on; a restrictive `definer_only` policy. Every definer takes
  `(session, stepup)`, the partner from the caller's live membership (`app_pm_live` / `app_partner_need`), matches every
  id on that partner (`not_found` otherwise), `set search_path = ''`, revoked from `public, anon, authenticated,
  service_role`. Every write is counted first in its own statement (`app_partner_credit_try`). A1a later adds Admin's
  aggregates; C1 gives Admin nothing.
- **No credit figure is stored in a tenant row** (spec § 8): the Studio panel and cards read the door at render.

## Data (migrations from 0162; generated + one `--custom` for grants, RLS, policies, definers; proof § 89)
| Table | Holds | Notes |
|---|---|---|
| `partner_billing` | per partner: legal name, GSTIN (nullable), state code, address; alert switches (below 50, client 80%); new-site budget (default 300); gateway customer id, token id, token status, token max | one row per partner; GSTIN checked by `gstinValid`, state code from the GSTIN when present |
| `partner_credit_entries` | append-only movements: a **lot** entry (`grant`, `pack`, `credits`, `seat`) with `credits > 0` and `expires_at`; a **draw** (`reserve`, `settle`, `release`, `return`, `expire`) naming its `lot_id` and, but `expire`, its `use_id` | grant: 20 once per partner (unique partial index); seat lots expire at the end of the second month after the grant month; packs and typed credits 12 months; no UPDATE or DELETE from any definer |
| `partner_credit_uses` | one row per reserve: partner, shop (the link's tenant id), partner member, kind (`preview`, `turn`), label, reserved credits, settled credits, list cost (micro-USD), the day's rate (paise per USD), loading (basis points), loaded cost paise, `settled_at`, `returned_at`, `return_reason` | the turn's rate stored here (spec § 8); Usage reads this |
| `partner_seats` | one row per partner subscription: plan (`studio`, `plus`), `started_at`, `current_period_start/end`, `cancel_at`, `failed_at`, `ended_at`, next plan | the plan shown is derived from timestamps (`seatState`) |
| `partner_credit_purchases` | attempt rows: kind (`pack`, `credits`, `seat_start`, `seat_renewal`), credits, taxable, CGST, SGST, IGST, total (paise), receipt, gateway order id, payment id, test mode, `created_at`, `claimed_at`, `paid_at`, `failed_at`, `closed_at`, `notice_at` (pre-debit), invoice id | no tenant; one open seat attempt per seat |
| `partner_invoices` | issued tax invoices: purchase id (unique), number (`FRR/26-27/NNNNN` from `platform_counters` 'invoice', the merchant series; `T26-27` in test), buyer snapshot (name, GSTIN, state, address), lines, totals, `test`, `issued_at` | Rule 46 fields from billing's document engine; snapshotted at issue |
| `partner_client_budgets` | partner, shop, kind (`build` before handover, `month` after), credits, `set_by`, `set_at` | a shop must be the partner's live link; written by the owner only |
| `partner_credit_events` | the gateway's webhook events for partner purchases: our key (sha256 of the signed body), event, order id, payment id, amount, currency, status, `received_at`, `applied_at` | trimmed as billing's route trims; no payer fields |
| `partner_credit_tries` | the write counter (P2's `partner_bill_tries` pattern) | rate limits: purchases 10 an hour a person, budget writes 60 an hour |

## Speed
Each tab is one definer call in one short transaction; balance and lots read on `(partner_id, lot_id)`; Usage pages 50
rows on `(partner_id, created_at, id)`; budgets on `(partner_id, shop_id)`. EXPLAIN at a 10× seed (1,000 partners × 2,000
uses a month). The door's reserve takes `for update` on the partner's `partner_billing` row only (serialises one
partner's reserves, never another's). The renewal run is batched in the existing daily outbox cron within its budget.
